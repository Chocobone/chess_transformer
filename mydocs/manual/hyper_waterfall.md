# Hyper-Waterfall: AI 시대의 소프트웨어 개발 방법론

> AI가 없던 시대에는 불가능했던 방법론.
> 워터폴의 규율과 애자일의 속도를 동시에.

## 1. 왜 새로운 방법론이 필요한가

### 워터폴의 실패

```
요구분석 ──→ 설계 ──→ 구현 ──→ 테스트 ──→ 배포
(2주)       (2주)    (4주)    (2주)      (1주)
```

워터폴은 올바른 철학을 가지고 있었다 — 계획하고, 문서화하고, 검증하라. 하지만 **속도가 너무 느렸다.**

### 애자일의 타협

애자일은 속도를 얻었지만 대가가 있었다:
- **문서가 사라졌다** — "코드가 곧 문서"라는 변명
- **방향이 흔들렸다** — 스프린트마다 우선순위가 바뀜
- **기술 부채가 쌓였다** — "나중에 리팩토링하자"가 영원히 미뤄짐

### 바이브 코딩의 함정

```
"AI야 만들어줘" → [수락] → [수락] → [수락] → ... → 💥
```

계획도 없고, 문서도 없고, 검증도 없다. **이해하지 못한 코드는 고칠 수도 없다.**

## 2. Hyper-Waterfall 정의

### 핵심 원리

**거시적으로는 워터폴, 미시적으로는 애자일 — AI가 이 둘을 동시에 가능하게 한다.**

```
거시 (프로젝트 수준) — 워터폴의 규율:
  계획 ──→ 설계 ──→ 구현 ──→ 검증 ──→ 배포
  │         │        │        │        │
  ▼         ▼        ▼        ▼        ▼
  문서화    문서화    문서화    문서화    문서화

미시 (타스크 수준, 수 시간) — 애자일의 속도:
  구현 → 테스트 → 피드백 → 수정 → 테스트 → ... (빠른 반복)
  │       │         │        │       │
  AI     자동화    사람 판단   AI    자동화
```

- **AI가 계획서를 쓰고** → 사람이 검토/승인 (10분)
- **AI가 코드를 작성하고** → 사람이 방향 제시 (1시간)
- **AI가 테스트를 만들고** → CI가 자동 검증 (2분)
- **AI가 문서를 정리하고** → 사람이 확인 (5분)

**규율은 그대로, 속도만 100배.**

## 3. 핵심 원칙

### 제 1원칙: 구현 목표가 AI 컨텍스트에 유지되도록 한다

- **CLAUDE.md**에 프로젝트 규칙, 빌드 방법, 워크플로우를 명시
- **타스크 등록 시** 목표와 범위를 명확히 기술
- **컨텍스트가 길어지면** 핵심 맥락을 요약하여 재주입

### 제 2원칙: 작업 통제권을 작업지시자가 유지해야만 한다

- **계획은 AI가 제안하되, 승인은 사람이 한다**
- **AI가 임의로 작업 종료를 제안하지 않는다** — 작업지시자가 결정
- **아키텍처 변경은 반드시 사람의 판단을 거친다**
- **"좋은 것 같습니다"로 넘어가지 않는다** — 직접 검증한다

### 제 3원칙: 주기적으로 AI 컨텍스트 유지를 확인해야 한다

- **컨텍스트 압축 시점**을 인지한다
- **핵심 결정사항을 문서로 외부화**한다
- **새 세션 시작 시** 이전 맥락을 요약하여 전달한다

## 4. 역할 분담

### 작업지시자 (사람)

- 방향 설정: "다음에 뭘 해야 하는가?"
- 우선순위: "무엇이 더 중요한가?"
- 품질 판단: "이것이 충분히 좋은가?"
- 아키텍처 결정: "이 구조가 올바른가?"
- 피드백: "이 부분이 잘못되었다, 왜냐하면..."

### AI 페어 프로그래머

- 분석: 코드베이스 탐색, 원인 추적
- 계획: 구현 계획서 작성
- 구현: 코드 작성, 테스트 생성
- 문서: 보고서, 기술 문서, 커밋 메시지

> **사람은 절대 생각을 멈추지 않는다.**

## 5. 타스크 사이클

```
1. 타스크 등록
   └─ 작업지시자: GitHub Issue 생성, 범위 정의

2. 수행 계획서
   └─ AI: 계획서 작성 (최소 3단계, 최대 6단계)
   └─ 작업지시자: 검토 → 승인 또는 수정 요청

3. 단계별 구현
   └─ AI: 코드 작성 + 테스트
   └─ AI: 단계 완료 보고서 작성
   └─ 작업지시자: 검증 → 승인 또는 피드백

4. 피드백 반영
   └─ 작업지시자: 피드백 문서 작성 (mydocs/feedback/)
   └─ AI: 피드백 반영, 수정

5. 최종 보고
   └─ AI: 최종 결과 보고서 작성
   └─ 작업지시자: 승인 → 이슈 클로즈
```

## 6. 문서 구조

```
mydocs/
├── orders/yyyymmdd.md                    ← 오늘 할일 (타스크 목록 + 상태)
├── plans/task_{milestone}_{N}.md         ← 수행 계획서
├── plans/task_{milestone}_{N}_impl.md    ← 구현 계획서
├── working/task_{milestone}_{N}_stage{M}.md ← 단계별 완료 보고서
├── report/task_{milestone}_{N}_report.md ← 최종 결과보고서
├── feedback/                             ← 코드 리뷰 피드백
├── tech/                                 ← 기술 조사·분석
├── manual/                               ← 매뉴얼/가이드
└── troubleshootings/                     ← 트러블슈팅
```

이 문서들은 부담이 아니다 — **AI가 작성하기 때문이다.** 사람은 검토하고 승인할 뿐이다.

## 8. 결론

> AI는 배율기다. 프로세스가 없으면 빠른 혼돈을, 좋은 프로세스가 있으면 비범한 결과를 만든다.

Hyper-Waterfall은 AI 시대에 **잃어버린 규율을 되찾는 방법론**이다.
