## 범위

1. **학습 정의**: R1~R10을 ID별 설정(기사, α, λ, τ, seed, 출력 폴더)으로 정의하고, 학습 명령으로 바꿔 주는 모듈과 테스트를 만든다. R1·R2·R8만 실행할 수 있게 하고, 나머지는 "특성 구현 전"으로 막는다. `smoke` ID를 둔다
2. **입력 매니페스트**: 서버로 옮길 파일(`base_model/136M.pt`, `data/processed/{tal,karpov,smyslov}/` 4개 파일씩)의 크기와 SHA-256 목록, 그리고 서버에서 확인하는 스크립트
3. **환경 구성**: conda 환경 정의(`environment.yml`)와 설치 스크립트. 설치 스크립트는 CUDA 버전에 맞는 torch를 설치하고, 저장소 테스트와 GPU 인식까지 확인한다
4. **작업 스크립트**: `sbatch` 작업 스크립트와 제출 스크립트
   - 자동 재개(`--resume`): 같은 작업 안에서 다시 시도하고(기존 `train_player.sh` 방식), 시간 제한에 걸려 끝나지 않았으면 다음 작업을 이어서 제출한다
   - `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`를 쓴다
   - 기록: 코드 커밋 해시, 학습 설정, GPU 종류·메모리, 노드, Slurm 작업 ID, 시도별 시작·종료 시각과 종료 코드, 재개 step, GPU 사용량(60초마다)
5. **결과 회수**: 회수할 파일을 하나로 묶는 스크립트. 대상은 어댑터, `config.json`, `log.jsonl`, 실행 로그, 기록, SHA-256이다. 사용자는 이 묶음을 로컬로 가져와 `mydocs/test_result/`에 결과를 정리한다
6. **매뉴얼**: `gpu_train/README.md`(한국어). 순서는 저장소 받기 → 입력 옮기기 → 확인 → 환경 구성 → smoke → 본 학습 제출 → 상태 확인 → 결과 회수다
7. **문서 연결**: 기준 문서 8.2절 정정, `mydocs/manual/training_guide.md`와 `README.md`에서 `gpu_train/` 링크

## 핵심 설계 원칙

- **학습 코드(`src/`)는 바꾸지 않는다.** `train.py`에 이미 `--seed`, `--resume`, `--max-steps`가 있다. `gpu_train/`는 이것을 부르는 얇은 층이다. 바꿔야 할 것이 나오면 멈추고 따로 승인을 받는다
- **학습 설정은 한곳에서 정의한다.** R1~R10의 인자는 학습 정의 모듈에만 둔다. 작업 스크립트는 ID만 받는다. 공통 설정은 Task #2~#4와 같고(기준 문서 8.1절), 기존 어댑터와 다른 값은 seed(1)뿐이다
- **서버 고유 값은 저장소에 넣지 않는다.** 파티션, 계정, 경로 같은 값은 설정 파일 하나(예: `gpu_train/site.env`, git 제외)에 모으고, 저장소에는 예시 파일만 둔다
- **재현 기록을 남긴다.** 결과 묶음만 보고도 어떤 코드, 설정, 입력, 장비로 학습했는지 알 수 있게 한다. 입력 SHA-256 확인을 통과해야 학습을 시작한다
- **로컬에서 확인할 수 있는 것은 로컬에서 확인한다.** 학습 정의와 명령 생성은 pytest로, 셸 스크립트는 문법 검사로 확인한다. 작업 스크립트는 Slurm이 없는 환경에서도 같은 본문을 실행하는 모드로 로컬 GPU smoke를 돌린다. Slurm과 conda 설치는 로컬에서 확인할 수 없으므로 서버 smoke 결과로 확인한다

## 기존 구현 현황

- `src/train/train.py`: 학습 진입점. `--player --base --out --seed --resume --max-steps --eval-every --checkpoint-every --num-workers`
- `runs/logs/train_player.sh` (git 제외, `mydocs/manual/training_guide.md` 6절에 원문): 자동 재시도(최대 10회, 진전 없이 3회 실패하면 중단), GPU 사용량 기록
- `requirements.txt`: torch, chess, numpy, pytest, 대국 앱 의존성(fastapi, uvicorn, httpx)
- `docker/`: 로컬 개발용 컨테이너. 이번 타스크에서 바꾸지 않는다
- 입력 파일 (git 제외)
  - `base_model/136M.pt`: 546 MB
  - `data/processed/{player}/`: `train.jsonl`, `val.jsonl`, `stats.json`, `base_q_136M.npz`, 합계 약 110 MB

## 서버 설정 파일의 빈칸

작업지시자가 설정 파일(`gpu_train/site.env`, git 제외)의 빈칸을 직접 채운다. 저장소에는 빈칸과 설명이 있는 예시 파일(`site.env.example`)만 둔다. 매뉴얼에는 항목마다 확인하는 명령(`sinfo`, `sacctmgr`, `nvidia-smi` 등)을 적는다.

| 항목 | 쓰는 곳 | 빈칸일 때의 처리 |
|---|---|---|
| 파티션, 계정(account), QoS 이름 | `#SBATCH` 헤더 | 설정 파일 값으로 채운다 |
| GPU 종류와 메모리, 작업당 GPU 요청 방식(`--gres=gpu:1` 등) | 헤더, 메모리 한도 판단 | `--gres=gpu:1` |
| 작업 하나의 최대 실행 시간 | 이어서 제출할지 여부 | 이어서 제출을 항상 켜 둔다 |
| CUDA 드라이버 버전 (`nvidia-smi`) | torch 휠 선택 | 설치 스크립트가 확인해 고른다 |
| 로그인 노드의 인터넷 연결 | conda와 pip 설치 | 연결이 있다고 가정한다. 없으면 오프라인 설치를 매뉴얼에 추가한다 |
| 저장소와 데이터를 둘 경로 (home, scratch), 계산 노드에서 공유되는지 | 경로 설정 | 설정 파일 값 |
| 같은 사용자의 GPU 작업 동시 실행 허용 | R1·R2·R8 동시 제출 | 하나씩 제출하는 방법도 적는다 |

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 서버 GPU에서 로컬과 다른 결과가 나온다 | 수치가 같을 필요는 없다(seed 1은 새 학습이다). 대신 smoke에서 기준선(baseline) 지표가 로컬 기록과 같은지 확인한다. 기준선은 캐시된 q로 계산하므로 장비와 관계없이 같아야 한다 |
| 시간 제한으로 작업이 중간에 끝난다 | 체크포인트(200 갱신마다)와 `--resume`으로 이어서 제출한다. 잃는 갱신은 최대 200개(약 4~5분)다 |
| 이어서 제출이 끝없이 반복된다 | 체크포인트가 전진하지 않으면 다음 작업을 제출하지 않는다. 이어서 제출하는 횟수에도 상한을 둔다 |
| 입력 파일이 옮기는 중에 손상된다 | SHA-256 확인을 통과해야 학습을 시작한다 |
| Python과 torch 버전이 로컬(3.13)과 다르다 | `environment.yml`에 Python 버전을 고정한다. torch는 서버 CUDA에 맞춘 버전을 기록에 남긴다. 설치 스크립트가 pytest를 돌려 동작을 확인한다 |
| 로컬에서 Slurm을 확인할 수 없다 | 작업 스크립트의 Slurm 밖 실행 모드로 본문을 로컬에서 확인한다. Slurm 고유 부분(헤더, 이어서 제출)은 서버 smoke로 확인하고, 결과를 사용자가 `mydocs/test_result/`에 저장한다 |

- 로컬 개발용 `docker/` 수정

## 예상 단계: 4단계

1. **학습 정의와 입력 매니페스트**: 학습 정의 모듈과 테스트, SHA-256 목록과 확인 스크립트
2. **환경 구성**: `environment.yml`, 설치 스크립트, 서버 설정 예시 파일
3. **작업 스크립트**: `sbatch` 작업 스크립트, 제출 스크립트, 재시도·이어서 제출·기록. 로컬에서 Slurm 밖 실행 모드로 smoke
4. **결과 회수와 문서**: 회수 스크립트, `gpu_train/README.md`, 기준 문서 8.2절 정정, 학습 가이드와 README 링크

서버 smoke는 4단계 뒤에 사용자가 서버에서 실행한다. 결과를 `mydocs/test_result/task_m100_10_test.md`에 저장해 주시면 최종 보고서에서 확인한다.
