## 수행 목표

270M 베이스(`base_model/270M.pt`)로 세 기사(탈·스미슬로프·카르포프)의 LoRA 어댑터를 GPU 서버에서 **바로 제출할 수 있는 상태**를 만든다. 끝 상태는 다음과 같다.

- 세 기사의 270M 베이스 q 캐시 `base_q_270M.npz`가 서버 입력(HF 리비전, `inputs.sha256`)에 들어 있다
- `gpu_train/runs.py`에 270M 학습 정의가 있고 `bash gpu_train/submit.sh <ID>`로 낼 수 있다
- 서버(RTX A2000 6 GB)에서 270M smoke 학습이 통과했고, 실측 메모리로 합법수 한도와 학습 1회 시간 추정을 정했다

본 학습(270M 어댑터 3개)은 이 타스크에서 하지 않는다. #13(서버 대국)은 2026-11-18에 끝나 `devel`에 반영됐다.

## 범위

1. **270M 학습 정의**: `runs.py`의 `Run`에 베이스와 합법수 한도를 받게 하고 270M 정의를 추가한다. 136M 정의(R1~R10, R1s0 등)가 만드는 명령은 한 글자도 바뀌지 않아야 한다(테스트로 고정)
2. **q 캐시 생성**: 세 기사의 `base_q_270M.npz`를 float32로 만든다 (결정 3)
3. **서버 입력 갱신**: `make_manifest.sh`에 270M 파일 4개를 넣고 HF에 올려 `inputs.hf` 리비전을 갱신한다 (업로드는 쓰기 토큰이 있는 작업지시자)
4. **270M smoke와 실측**: 서버에서 270M smoke(50 갱신, 평가 2회)를 돌려 학습·평가 메모리와 처리량을 잰다. 결과로 합법수 한도(`--max-moves-per-forward`, 필요하면 평가 묶음)와 학습 1회 시간, 이어서 제출 수를 정한다
5. **문서**: `gpu_train/README.md`, `mydocs/manual/training_guide.md`에 270M 실행 방법과 실측을 적고, 결과를 `mydocs/test_result/task_m100_14_test.md`로 정리한다

## 핵심 설계 원칙

- **136M 경로 무변경**: 기존 학습 ID의 명령, 기존 입력 파일의 SHA-256은 그대로 둔다. 새 매니페스트는 기존 13개 + 270M 4개다
- **서버 입력 교체 순서**: `train`·`eval`·`dump` 작업은 시작할 때 `check_inputs.sh`로 매니페스트 전체를 확인한다. 서버에서 새 매니페스트를 `git pull`하고 `fetch_inputs.sh`를 하기 전에 대기 중인 작업이 시작하면 입력 확인 실패(종료 코드 2)로 끝난다. 그래서 서버 배포는 **`git pull` 직후 바로 `fetch_inputs.sh`** 하고, 대기 중인 학습·덤프 작업이 없을 때 한다. #13의 서버 작업은 모두 끝났다 (`match`·`quality` 작업은 `check_inputs.sh`를 쓰지 않는다)
- **결과가 바뀌지 않는 설정만 조정**: 합법수 한도는 기울기 누적 단위만 바꾸고 학습 결과는 같다(학습 가이드 6절). 270M과 136M의 학습 설정 차이는 `--base`와 한도뿐으로 둔다

## 위험과 대응

| 위험 | 대응 |
|---|---|
| A2000 6 GB에서 270M 학습이 메모리 부족 | 계산상 한도 48 근처(가중치 약 1.1 GB + 65 MiB × 48 ≈ 4.2 GiB)부터 smoke로 잰다. 부족하면 32로 낮춘다 |
| 학습 중 평가(합법수 256개, float32)가 메모리 부족 | smoke에 평가 2회를 넣어 확인한다. 부족하면 `--eval-max-moves`를 낮춘다(평가 값은 묶음 크기와 무관) |
| 서버 학습 시간이 길다 | 136M 서버 실측 8~10시간/회, 270M은 연산량이 약 2배라 약 18~25시간/회로 본다(추정). smoke 처리량으로 확정하고 `SBATCH_TIME`·`CHAIN_MAX`를 확인한다 |

| 캐시가 데이터와 어긋난다 | 학습 시작 시 국면 수·수 순서 검사가 있다(학습 가이드 5절). 추가로 기사마다 국면 일부를 로컬 CPU에서 다시 계산해 비교한다 |
