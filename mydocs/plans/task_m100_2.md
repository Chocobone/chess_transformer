# Task #2: 기사별 LoRA 어댑터 본 학습 (탈·카르포프·스미슬로프, 136M) — 수행 계획서

## 수행 목표

Task #1에서 작성한 전처리·학습 코드로 탈·카르포프·스미슬로프 세 기사의 LoRA 어댑터를 실제로 학습한다.
베이스는 136M, 실행 위치는 로컬 개발 컨테이너의 GPU(RTX 4070 Ti 12GB)다.
산출물은 기사별 어댑터 3개(`runs/{player}_136M/adapter.pt`)와, 베이스 기준선 대비 val 지표 변화를 정리한 학습 결과 문서다.

## 범위

1. **베이스 q 캐시 생성**: 세 기사의 train·val 전 국면에 대해 136M 베이스의 q(s, a)를 float32로 계산
2. **LoRA 어댑터 학습**: 세 기사에 같은 설정으로 학습
3. **결과 정리**: 실행 명령, 설정, 베이스 기준선, val 지표 추이를 `mydocs/test_result/task_m100_2_test.md`에 기록
4. **학습 실행 중 드러나는 코드 문제 수정**: 발생하면 원인과 수정안을 보고하고 승인 후 수정

### 범위 외 (후속 타스크)

- 270M 베이스 학습
- 스타일 특성 벡터 f(s,a) 라벨링, 방향 벡터 w_p 추정, 스타일 항 학습
- α 스윕, 평가(지문 거리·혼동 행렬·대국 성적)
- 학습된 어댑터가 기사의 스타일을 반영하는지에 대한 판단. 이 타스크는 val 모방 지표와 기력 지표까지만 본다

## 핵심 설계 원칙

- **세 기사에 같은 설정**: `--player`만 다르다. 한 기사의 결과를 보고 설정을 바꾸면 이미 학습한 기사도 새 설정으로 다시 학습한다.
- **먼저 한 기사로 확인하고 나머지를 돌린다**: 탈을 먼저 끝까지 학습해 결과를 보고한 뒤, 승인을 받고 카르포프·스미슬로프를 학습한다. 설정이 부적절한 경우 9시간이 아니라 3시간만 잃는다.
- **결과는 있는 그대로 기록한다**: 지표가 좋아지지 않았거나 나빠진 경우에도 수치를 그대로 적는다. Task #1의 확인 학습에서 top-1 일치율은 변하지 않았다.
- **소스는 가능한 한 그대로 쓴다**: 이 타스크의 중심은 실행이다. 코드 수정은 아래 "결정이 필요한 사항"에서 승인된 것과, 실행 중 발견된 문제에 한정한다.

### 데이터 규모와 예상 소요 시간

갱신 횟수는 train 국면 수 × 3 epoch ÷ 32로 계산했다. 시간은 Task #1에서 잰 처리량(캐시 약 880 수/초, 학습 갱신당 약 1.3초)으로 계산한 추정이며, 전체 데이터로 잰 값이 아니다.

| 기사 | train 국면 | val 국면 | 갱신 횟수 | 학습 시간 (추정) |
|------|-----------|----------|-----------|------------------|
| 탈 | 79,493 | 3,880 | 7,452 | 약 2.7시간 |
| 카르포프 | 96,393 | 5,213 | 9,037 | 약 3.3시간 |
| 스미슬로프 | 93,178 | 4,753 | 8,735 | 약 3.2시간 |

| 구간 | 추정 시간 |
|------|-----------|
| q 캐시 (세 기사 합계) | 약 2.8시간 |
| 학습 (세 기사 합계) | 약 9.1시간 |
| 학습 중 val 평가 (세 기사 합계, 아래 결정 2에 따라 달라짐) | 약 1.5~3시간 |
| **합계** | **약 13.5~15시간** (승인 대기 시간 제외) |

val 평가 시간은 실측한 적이 없다. val 전체를 float32로 한 번 도는 데 약 2.5~3.5분으로 추정했고, 1단계의 사전 확인에서 실제 값을 재어 보고한다.

## 학습 설정 (안)

`training_guide.md`의 기본값을 그대로 쓴다. Task #1 보고서가 "첫 학습 결과를 보고 정할 것"으로 남긴 값들이므로, 탈 학습 결과를 보고 유지 여부를 판단한다.

| 옵션 | 값 | 비고 |
|------|-----|------|
| `--base` | `base_model/136M.pt` | 작업지시자 결정 |
| `--rank`, `--lora-alpha` | 16, 32 | 기본값 |
| `--lora-targets` | `q k v o` | 기본값 |
| `--temperature` | 0.02 | 기본값 |
| `--lam`, `--tau` | 1.0, 0.02 | 기본값. 기력 항이 모방 항의 0.3% 수준이라 실제 제약으로 작동하는지는 미확인 (Task #1 발견 사항 6) |
| `--gamma`, `--alpha` | 0.0, 0.0 | 기본값. 스타일 항은 비활성 |
| `--lr`, `--epochs` | 1e-4, 3 | 기본값 |
| `--batch-positions` | 32 | 기본값 |
| `--max-moves-per-forward` | 128 | 기본값. 136M에서 약 4.7 GiB |
| `--eval-every` | 아래 결정 2 | |
| `--seed` | 0 | 기본값 |

q 캐시는 float32(기본값)로 만든다. `--amp`는 2.5배 빠르지만 q가 τ에 비해 무시하기 어려운 만큼 달라져 쓰지 않는다.

## 실행 방식

- 캐시와 학습은 세션과 분리된 백그라운드 프로세스로 돌리고 표준 출력을 `runs/` 아래 로그 파일에 남긴다. 한 번에 하나만 GPU에 올린다 (동시에 올리면 서로 느려지고 메모리 초과 위험이 있다).
- 진행은 `log.jsonl`과 로그 파일로 확인한다. `max_memory_gib`와 `positions_per_sec`를 보고 메모리 초과(WSL에서는 실패 대신 수십 배 느려짐)를 감시한다.
- `runs/`와 `data/`는 git 제외 대상이다. 어댑터 파일은 저장소에 올라가지 않으므로, 결과 문서에 파일 크기와 SHA-256을 적어 어떤 파일의 결과인지 식별할 수 있게 한다.

## 결정이 필요한 사항

1. **학습 재개(resume) 기능을 이 타스크에서 추가할지**
   - 안 A (권장): 추가하지 않는다. 기사별 학습이 약 3시간이라 중단 시 손실이 그 범위이고, 어댑터는 평가 때마다 저장된다. 소스 수정 없이 바로 실행할 수 있다.
   - 안 B: 추가한다. 옵티마이저·스케줄러·난수 상태·스텝을 저장하고 이어서 돌리는 기능과 테스트를 1단계 앞에 넣는다. 구현·검증에 시간이 들고, 재개한 학습이 끊기지 않은 학습과 같은 결과를 내는지 확인해야 한다.
2. **평가 주기 `--eval-every`**
   - 안 A (권장): 1000. 기사당 평가 8~10회, 세 기사 합계 약 1.5시간(추정). 3 epoch 동안 지표 추이를 보기에 충분하다.
   - 안 B: 500 (기본값). 기사당 15~19회, 합계 약 3시간(추정). 추이가 더 촘촘하다.
3. **탈 결과 확인 후 진행 방식**: 위 원칙대로 탈 학습 후 보고·승인을 거쳐 나머지 두 기사를 돌린다 (권장). 승인 대기 없이 세 기사를 연달아 돌리기를 원하면 2·3단계를 합친다.

## 학습 재개 기능 추가 (2026-10-12 작업지시자 지시)

확정 사항 1번("학습 재개 기능은 추가하지 않는다")을 바꿔 **재개 기능을 추가한다.**

**배경**: 2026-10-12에 탈 학습이 두 번 중단되었다.

| 실행 | 시작 | 중단 | 중단 지점 | 오류 |
|------|------|------|-----------|------|
| 1차 | 02:07:51 | 02:52:18 (44분) | 1,840 갱신 직후 | `CUDA error: device-side assert triggered` (gather 인덱스 범위 초과) |
| 2차 | 03:11:15 | 04:49:41 (98분) | step 4000 평가·저장 직후 | `CUDA error: unspecified launch failure` |

- 두 실행은 같은 명령·같은 seed이고, 1차가 중단되기 전까지의 train 기록 92줄이 2차와 완전히 같다. 2차는 1차의 중단 지점을 문제없이 지났다. 같은 입력에서 중단 지점과 오류 종류가 매번 다르므로 코드·데이터의 결정적 결함이 아니라 실행 환경(GPU·드라이버·WSL2)의 불안정으로 판단한다. 무엇이 일으키는지는 확인하지 못했다.
- 1차 중단 구간(step 1801~1900)의 배치를 같은 seed로 복원해 GPU에서 순전파·손실 계산을 다시 했을 때 오류는 재현되지 않았고 토큰 범위도 정상이었다.
- 재개 기능이 없으면 중단될 때마다 처음부터 다시 돌아야 한다. 44분·98분 만에 중단되는 환경에서 3~4시간짜리 학습이 끝까지 가기를 기대하기 어렵다.

**범위**: `src/train/train.py`에 체크포인트 저장과 `--resume`을 추가하고 `tests/test_train.py`에 테스트를 추가한다. 손실·모델·데이터 코드는 건드리지 않는다. 구현 내용과 검증은 구현 계획서 2단계에 적는다.

**원칙**

- 재개한 학습은 끊기지 않은 학습과 같은 결과를 내야 한다. 테스트로 확인한다.
- 재개 기능을 넣어도 끊기지 않은 학습의 결과(배치 순서, 수치)는 수정 전과 같아야 한다. 수정 전 실행의 기록과 대조해 확인한다.
- 중단 원인 자체는 이 타스크에서 해결하지 않는다. GPU 전체 사용량을 기록해 원인 추정의 근거만 남긴다.
