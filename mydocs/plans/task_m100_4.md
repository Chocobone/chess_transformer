# Task #4: 스미슬로프 LoRA 어댑터 본 학습 (136M) — 수행 계획서

## 수행 목표

탈(Task #2)·카르포프(Task #3)에 쓴 것과 같은 코드·같은 학습 설정으로 스미슬로프의 LoRA 어댑터를 3 epoch(8,736 갱신) 끝까지 학습한다.
베이스는 136M, 실행 위치는 로컬 개발 컨테이너의 GPU(RTX 4070 Ti 12GB)다.
카르포프 학습에서 학습 중 val 평가가 크게 느려졌으므로(10회에 약 3.5시간), 본 학습 앞에 사전 측정과 대책 결정을 둔다.
산출물은 어댑터(`runs/smyslov_136M/adapter.pt`)와 학습 결과 문서(`mydocs/test_result/task_m100_4_test.md`)다.

## 범위

1. **사전 확인**: `pytest`, 스미슬로프 q 캐시의 SHA-256 대조, GPU 상태(학습 전 데스크톱 사용량 기록), 실행 스크립트 점검
2. **사전 측정**: 스미슬로프로 짧은 학습(60 갱신) 뒤 val 전체 평가가 도는 실행을 돌려, 평가 전후의 GPU 전체 사용량과 평가 시간을 잰다
3. **대책 비교와 결정**: 측정이 아래 "정상 기준"을 벗어날 때만 한다. 대책별로 같은 측정을 반복해 평가 시간, GPU 전체 사용량, 지표가 바뀌지 않는지를 본다. 결정은 작업지시자가 한다
4. **스미슬로프 어댑터 학습**: `--resume`과 자동 재시도 스크립트 사용. 학습 중 감시와 멈출 기준은 아래 수치대로
5. **학습 검증과 결과 정리**: 로그 연속성, 어댑터 재평가, 탈·카르포프와의 설정 대조. 결과를 `mydocs/test_result/task_m100_4_test.md`에 기록

### 범위 외

- 세 기사 결과 종합, `mydocs/manual/training_guide.md` 갱신 (별도 이슈). 탈·카르포프 결과와의 비교는 하지 않는다. 설정이 같은지만 확인한다
- 카르포프 학습 구간의 처리량 저하(step 4,260~6,200), 평가 시간이 뒤로 갈수록 늘어난 이유의 원인 규명. 스미슬로프에서 같은 일이 일어나면 기록하고 멈출 기준대로 대응한다
- 탈·카르포프 어댑터의 재학습. 대책으로 설정이 달라지더라도 이 타스크에서 다시 돌리지 않는다
- 270M 베이스 학습, 스타일 항 학습, α 스윕, 평가(지문 거리·혼동 행렬·대국 성적)
- 어댑터가 스미슬로프의 스타일을 반영하는지에 대한 판단. val 모방 지표와 기력 지표까지만 본다

## 핵심 설계 원칙

- **학습 설정은 탈·카르포프와 같게 둔다**: 학습 결과에 영향을 주는 값(rank, 학습률, epoch, 배치, seed 등)은 바꾸지 않는다. 대책으로 바꿀 수 있는 것은 평가의 묶음 크기와 메모리 할당 방식뿐이며, 바꾸면 지표가 같다는 확인을 기록한다.
- **재고 나서 정한다**: 어제의 어림(학습 중 GPU 전체 11.1~11.9 GiB)은 탈 한 번의 관찰에 기댄 것이라 근거가 약하다. 본 학습 전에 실측한다.
- **멈출 기준을 수치로 둔다**: 카르포프에서는 "급격히 떨어지면 멈춘다"가 모호해 판단이 늦었다. 아래 "학습 중 감시"의 수치를 쓴다.
- **소스 수정은 승인 후에만**: 대책 (가)·(나)는 소스 수정이 없다. (다)는 `src/train/train.py` 수정이므로 택하면 수정안을 구현 계획서에 넣어 따로 승인받는다.
- **결과는 있는 그대로, 수치는 스크립트로**: 나빠진 지표도 그대로 적고, 결과 문서의 표는 `log.jsonl`에서 스크립트로 뽑는다.

### 학습 명령과 설정 (대책이 필요 없을 때)

```bash
python -u -m src.train.train --player smyslov --base base_model/136M.pt \
    --out runs/smyslov_136M --eval-every 1000 --resume
```

나머지는 기본값이다 (rank 16, lora-alpha 32, targets q k v o, T 0.02, λ 1.0, τ 0.02, γ 0, α 0, lr 1e-4, 3 epoch, 국면 32개/갱신, 합법수 한도 128, `--eval-max-moves 256`, `--checkpoint-every 200`, seed 0). 실제 실행은 `runs/logs/train_player.sh smyslov`를 `setsid nohup`으로 세션과 분리해 돌린다. 로그는 `runs/logs/train_smyslov_136M.log`.

## 사전 측정

```bash
python -u -m src.train.train --player smyslov --base base_model/136M.pt \
    --out runs/smyslov_probe_base --max-steps 60 --eval-every 20
```

- 본 학습과 겹치지 않도록 `--out`을 따로 둔다. 끝나면 `runs/smyslov_probe_*`는 남겨 두되 본 학습에는 쓰지 않는다.
- `--eval-every 20`으로 평가가 3회(step 20, 40, 60) 돈다. 평가가 거듭될 때 사용량이 더 오르는지 보기 위해서다 (결정 사항 1).
- GPU 전체 사용량·온도·전력은 `nvidia-smi`로 5초마다 따로 기록하고, 평가 시간은 표준 출력의 줄마다 시각을 붙여 잰다. 소스 수정 없음.
- 예상 소요: 로드·기준선 약 1.5분 + 60 갱신 80초 + 평가 3회 약 10분 = 약 13분.

**정상 기준** (셋 모두 만족하면 대책 없이 본 학습으로 간다):

| 항목 | 기준 | 근거 |
|------|------|------|
| 평가 1회 시간 | 세 번 모두 260초 이하 | 단독 측정 201초의 1.3배 |
| GPU 전체 사용량 최대 | 11.0 GiB 이하 | 12.0 GiB 카드에서 1 GiB 여유. 탈에서 이후 평가로 0.5 GiB 더 올랐다 |
| 평가 사이의 증가 | 3회째 평가 뒤 사용량이 1회째 뒤보다 0.3 GiB 넘게 오르지 않는다 | 계속 오르면 본 학습의 9회 평가 안에 넘친다 |

측정 때의 데스크톱 사용량도 함께 적는다. 지금 1.2 GiB로 어제보다 크다. 학습 전에 호스트의 다른 GPU 사용(브라우저 등)을 줄일 수 있으면 여유가 그만큼 늘어난다.

## 대책 (정상 기준을 벗어날 때)

| 안 | 내용 | 소스 수정 | 걸리는 점 |
|----|------|-----------|-----------|
| (가) | `--eval-max-moves`를 줄인다 (128, 필요하면 64) | 없음. 다만 `train_player.sh`가 인자를 고정하고 있어 스크립트(git 제외)에 인자 전달을 넣어야 한다 | `config.json`의 `eval_max_moves`가 탈·카르포프와 달라진다. 묶음이 작아져 평가가 느려질 수 있다 |
| (나) | 환경변수 `PYTORCH_CUDA_ALLOC_CONF`로 할당 방식을 바꾼다 (`expandable_segments:True` 등. 이 환경에서 듣는지는 돌려 봐야 안다) | 없음. 환경변수는 스크립트가 그대로 넘겨준다 | 학습 구간의 할당에도 영향을 준다. 학습 처리량과 결과가 같은지 확인이 필요하다 |
| (다) | 평가 전후에 예약 메모리를 비운다 (`torch.cuda.empty_cache()`) | **있음** (`src/train/train.py`) | 계획서·승인·테스트가 필요하다. 탈·카르포프와 코드가 달라진다 |

- 각 안을 사전 측정과 같은 명령에 그 안만 더해 돌린다 (`runs/smyslov_probe_{이름}`). 한 번에 약 13분.
- 볼 것: 평가 시간, GPU 전체 사용량 최대, 60 갱신 구간의 처리량, **step 20·40·60의 val 지표 7개가 기준 측정과 같은지**. 같은 seed의 60 갱신은 재현되므로(Task #2 재개 확인) 지표를 직접 대조할 수 있다. (가)는 묶음 경계가 달라 합산 순서에 따른 차이(1e-7 수준)는 날 수 있다. 그보다 크면 그 안은 쓰지 않는다.
- (가) → (나) 순으로 본다. 둘 다 기준에 못 미칠 때만 (다)의 수정안을 만들어 보고한다.
- 결과를 표로 보고하고 **작업지시자가 정한다**.

## 학습 중 감시

20~30분 간격으로 `log.jsonl`, `gpu_mem_smyslov_136M.log`를 확인한다. 아래 중 하나에 해당하면 **다음 체크포인트 직후에 학습을 멈추고 보고한다** (체크포인트는 200 갱신마다, 약 4.5분 간격이라 잃는 갱신은 수 개 이내다. 재개는 `--resume`으로 된다).

| 항목 | 멈출 기준 |
|------|-----------|
| 평가 1회 시간 | 400초 초과 (사전 측정값의 약 2배) |
| 학습 구간 처리량 | 18 국면/초 미만이 10분(train 줄 약 20개) 넘게 이어짐. 정상은 약 24 |
| GPU 전체 사용량 | 11.8 GiB 이상 |

- 멈춘 뒤 다시 시작할지, 대책을 바꿀지는 작업지시자가 정한다. 임의로 재시작하지 않는다 (카르포프의 두 번째 재시작은 사전 승인 없이 했다).
- CUDA 오류로 끝나는 경우는 스크립트의 자동 재개에 맡기고 시각·step·오류를 기록한다.

## 결정이 필요한 사항

1. **사전 측정의 평가 횟수**
   - 안 A (권장): `--eval-every 20`으로 평가 3회 (약 13분). 평가가 거듭될 때 사용량이 오르는지까지 본다.
   - 안 B: 어제 이월 항목대로 평가 1회 (`--eval-every 1000`, 약 6분).
2. **정상 기준과 멈출 기준의 수치**: 위 표의 값(260초 / 11.0 GiB / 0.3 GiB, 400초 / 18 국면/초 / 11.8 GiB)으로 할지.
3. **호스트 확인** (작업지시자): 학습 중 Windows 작업 관리자의 "공유 GPU 메모리" 사용량, NVIDIA 제어판의 "CUDA - Sysmem Fallback Policy" 설정값, 절전 설정. Fallback이 "Prefer No Sysmem Fallback"이면 넘칠 때 느려지는 대신 오류로 끝나므로 대응 방식이 달라진다. 지금 값을 알려 주면 계획에 반영한다.
4. **학습 시작 시점**
   - 안 A (권장): 사전 측정(과 대책 비교) 결과를 보고하고 승인을 받은 뒤 학습을 시작한다.
