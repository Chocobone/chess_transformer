# Task #5: 학습 재개 시 데이터 순서 불일치 수정, 학습 기록 정정 — 수행 계획서

## 수행 목표

`--resume`으로 재개한 학습이 epoch 1 이후에서 끊기지 않은 학습과 다른 데이터 순서로 도는 문제를 고친다.
또 탈·카르포프·스미슬로프 학습 기록 가운데 잘못된 기술(중단 지점, 잃은 갱신 수, 재개 동일성 주장)을 바로잡고, 세 어댑터가 받은 영향의 추정치를 남긴다.

## 배경

### CUDA 오류는 가중치에 영향을 주지 않는다

device-side assert가 나면 프로세스가 끝나고, 실행 스크립트가 마지막 체크포인트부터 다시 시작한다. 실패한 시도에서 체크포인트 뒤에 한 갱신은 모두 버려진다. 따라서 체크포인트 재현을 통한 원인 조사와 성능 영향 실측은 하지 않는다 (작업지시자 결정, 2026-10-15).

### 재개 뒤 train 줄이 끊기기 전 시도와 다르다

실행 로그(`runs/logs/train_*_136M.log`)에는 실패한 시도의 줄과 재개한 시도의 줄이 모두 남아 있다. 같은 step끼리 비교하면 lr은 같고 loss·grad_norm이 다르다.

| 기사 | 재개 지점 (epoch) | 실패한 시도의 마지막 train 줄 | 비교 예 (step: 실패한 시도 / 재개한 시도의 loss) |
|------|------|------|------|
| 탈 | 4800 (epoch 1) | 5000 | 4820: 0.771 / 0.939, 5000: 1.364 / 0.688 |
| 스미슬로프 | 5400 (epoch 1) | 5580 | 5420: 1.424 / 1.017, 5580: 1.239 / 0.965 |
| 카르포프 | 6000 (epoch 1), 6200 (epoch 2) | 체크포인트 직후 종료(137)라 겹치는 줄 없음 | — |

### 원인

`src/train/train.py`는 데이터 순서용 생성기 `generator` 하나를 `RandomSampler`와 `DataLoader(generator=...)`에 함께 넘긴다. `DataLoader`는 반복자를 새로 만들 때마다 이 생성기에서 worker 시드를 하나 뽑는다.

- `num_workers=2`(본 학습 설정)에서는 `persistent_workers=True`라서 반복자를 처음 한 번만 만든다. epoch 1부터는 시드를 뽑지 않고 순열만 뽑는다.
- 재개한 프로세스는 epoch 시작 때의 생성기 상태를 복원한 뒤 반복자를 새로 만든다. 이때 시드를 한 번 더 뽑기 때문에 그 epoch의 순열이 밀린다.
- 그 결과 재개한 epoch에서는 "다른 순열의 앞부분을 건너뛴 나머지"를 학습한다. 일부 국면은 그 epoch에 두 번, 같은 양은 한 번도 학습되지 않는다.
- `num_workers=0`이면 매 epoch 반복자를 새로 만들므로 재개해도 순서가 같다. 기존 재개 테스트는 `--num-workers 0`이고, Task #2의 GPU 재개 검증(60 갱신)은 epoch 0 안에서만 끊어 이 문제를 잡지 못했다.
- 같은 이유로 끊기지 않은 학습도 `num_workers` 값에 따라 epoch 1부터 순서가 달라진다. 그런데 `--num-workers`는 재개 때 바꿔도 되는 인자(`RESUME_FREE_ARGS`)로 되어 있다.

CPU 소형 재현(데이터 40개, 배치 4, 2 epoch)으로 확인했다. `num_workers=0`에서는 끊기지 않은 실행과 재개한 실행의 epoch 1 순서가 같았고, `2`에서는 달랐다.

## 범위

1. **재개 순서 수정** (`src/train/train.py`): 데이터 순열이 재개 여부와 `num_workers`에 따라 달라지지 않게 한다. 방안은 아래에서 고른다.
2. **테스트 추가** (`tests/test_train.py`): `num_workers>0`에서 epoch 경계를 넘긴 뒤 멈추고 재개해도 끊기지 않은 학습과 같은지, `num_workers` 0과 2의 결과가 같은지 확인한다.
3. **기존 기록 정정**:
   - 중단 지점과 잃은 갱신 수: 스미슬로프는 "step 5,400~5,420, 20개 이내" → "step 5,580~5,600, 약 180개". 탈은 "step 4,800~4,820" → "step 5,000~5,020, 약 200개". 대상은 Task #2·#4의 단계·최종 보고서, 테스트 결과, 오늘할일(20261012, 20261014)
   - 재개 동일성 주장: `mydocs/manual/training_guide.md`의 "재개한 학습의 결과는 끊기지 않은 학습과 같다", "`--num-workers`는 바꿔도 된다"와, Task #2 보고서의 같은 취지 기술
   - 세 어댑터가 받은 영향의 추정치를 기록한다 (재개한 epoch에서 두 번 또는 0번 학습된 국면의 비율. 계산은 스크립트로 한다)
4. 기존 문서는 내용을 지우지 않고 정정 표시를 남긴다 (예: "정정 (2026-10-15, Task #5): …").

### 수정 방안 (구현 계획서에서 확정)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (추천)** | worker 시드용 생성기를 따로 두고(`DataLoader(generator=별도)`), 순서용 `generator`는 `RandomSampler`만 쓴다 | 순열이 반복자 생성 횟수와 무관해진다. 수정이 작다 | epoch 0부터 순서가 지금과 달라져 기존 어댑터의 배치 순서를 재현할 수 없다 (어차피 재개 구간은 재현되지 않는다) |
| B | 재개할 때 반복자를 만든 뒤 생성기 상태를 복원하는 식으로 지금 순서를 흉내 낸다 | 끊기지 않은 `num_workers=2` 학습의 기존 순서를 유지 | `num_workers` 값과 `DataLoader` 내부 동작에 기대므로 깨지기 쉽다. `num_workers` 의존성이 남는다 |

- A로 고치면 기존 체크포인트에서 재개할 때도 새 순서를 따르게 된다. 끝난 세 학습은 다시 돌리지 않으므로 실제 영향은 없지만, 체크포인트에 표시를 두어 옛 체크포인트로 재개할 때 경고하거나 거부할지는 구현 계획서에서 정한다.
