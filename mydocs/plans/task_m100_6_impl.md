# Task #6: 세 기사 136M 어댑터 학습 결과 종합, 실행 가이드 갱신 — 구현 계획서

## 공통

- 소스(`src/`, `scripts/`, `tests/`)는 수정하지 않는다. 집계·평가 스크립트는 스크래치패드에서 실행하고 저장소에 넣지 않는다. 쓴 스크립트의 핵심은 단계 보고서에 옮겨 적는다.
- GPU는 2단계에서만 쓴다. 실행 환경은 로컬 개발 컨테이너(WSL2), RTX 4070 Ti 12GB, 베이스 `base_model/136M.pt`다.
- 표의 수치는 스크립트 출력에서 옮긴다. 기존 보고서와 다르면 차이와 원인을 적는다. 기존 문서를 정정해야 하면 멈추고 따로 승인받는다.

**산출물 위치**

```
mydocs/tech/adapters_136M_summary.md      ← 기준 표 (1단계에 수치 종합, 2단계에 교차 평가 추가, 3단계에 완성)
mydocs/test_result/task_m100_6_test.md    ← 교차 평가 실행 기록 (명령, 시간, GPU 사용량, 원 출력)
mydocs/manual/training_guide.md           ← 3단계 갱신
runs/cross_eval_136M/                     ← 교차 평가 결과 JSON (git 제외)
runs/logs/cross_eval_136M*.log            ← 교차 평가 표준 출력, GPU 기록 (git 제외)
```

## 1단계: 수치 종합과 조건 차이 정리 (GPU 불필요)

### 목표

세 어댑터의 학습 조건과 결과를 같은 형식의 표로 만든다. 기존 보고서와 대조해 값이 맞는지 확인한다.

### 구현

1. **데이터 규모**: `data/processed/{player}/stats.json`과 `config.json`에서 국 수, train·val 국면 수, val 합법수 수를 뽑는다.
2. **설정 대조**: 세 `config.json`의 모든 키를 비교한다. 다른 키는 데이터에 따라 정해지는 값(`player`, `out`, `total_steps`, `train_positions`, `val_positions`)뿐인지 확인한다.
3. **val 지표**: `log.jsonl`의 baseline 줄과 eval 줄로 아래를 만든다.
   - 기준선 → 최종 표 (7개 지표, 변화량, 상대 변화)
   - 평가 시점별 곡선 표 (step 1000 단위). 학습 진행률(갱신 수 / 전체)로 맞춘 곡선도 함께 만든다. 학습률 일정이 진행률 기준이기 때문이다
   - imitation 개선의 몇 %가 첫 평가(step 1000)까지 났는지 비교한다
4. **학습 운영**: 실행 로그와 GPU 기록에서 아래를 뽑는다.
   - 시도별 시각, 소요 시간
   - 처리량 중앙값, `max_memory_gib`, GPU 전체 사용량 최대, 평가 회당 시간
   - 중단·재개 이력과 잃은 갱신 (Task #5 1단계 값 재사용, 대조)
5. **val 겹침 점검**: 교차 평가를 해석할 때 필요하다. 각 기사 val의 FEN 가운데 다른 기사 train에 같은 FEN이 있는 비율, 자기 train에 있는 비율을 센다. 대부분 오프닝 국면일 것이므로 ply 구간별로도 센다.
6. **조건 차이 표**: 재개 구간 데이터 순서(Task #5 추정치), `expandable_segments`(스미슬로프만), 평가 지연(카르포프), 중단 횟수와 원인.
7. `mydocs/tech/adapters_136M_summary.md` 초안을 쓴다.

### 완료 기준

- 위 표가 모두 스크립트 출력으로 채워진다.
- 기존 보고서(Task #2~#4 최종 보고서·테스트 결과)의 최종 지표, 소요 시간과 대조해 차이 목록을 만든다 (없으면 "없음").

## 2단계: 교차 평가 (GPU)

### 목표

각 어댑터를 세 기사의 val 전체에 평가해 3×3 표를 만든다. 같은 val에서 자기 기사 어댑터가 다른 기사 어댑터보다 기사의 수를 더 잘 맞히는지 본다.

### 방법

- 어댑터마다 새 프로세스 하나에서 베이스 `base_model/136M.pt`에 `load_adapter`로 어댑터를 붙인다. 그 뒤 탈·카르포프·스미슬로프 val을 차례로 평가한다 (프로세스 3개, 평가 9회).
- 평가 함수는 학습과 같은 `src.train.train.evaluate`를 쓴다. 설정도 학습과 같게 둔다: `Objective` 기본값(temperature 0.02, tau 0.02), `max_moves=256`, float32.
- 대각선 3칸은 학습 마지막 eval과 같아야 한다 (Task #4의 재평가에서 차이 0). 같지 않으면 멈추고 보고한다.
- **대국 단위 집계**: val을 `game_id`별로 묶는다. `evaluate`를 대국마다 호출해 대국별 지표 합과 국면 수를 저장한다. 대국별 값의 국면 가중 평균이 전체 평가와 같은지 확인한다.
- **불확실성**: 같은 val에서 "자기 어댑터 − 다른 어댑터"의 imitation·top1 차이에 대해 대국 단위 부트스트랩(10,000회, seed 0) 95% 구간을 낸다. 같은 대국의 국면끼리는 서로 독립이 아니므로 대국을 단위로 한다.
- 베이스 기준선(각 val의 baseline 줄)과 함께 놓고, 각 어댑터가 각 val에서 기준선 대비 얼마나 좋아졌는지도 표로 만든다.
- 실행: `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, 표준 출력과 GPU 사용량(60초마다)을 `runs/logs/`에 남긴다. 예상 시간은 평가당 약 3~4분, 합계 약 30~40분이다.

### 멈출 기준

- 평가 한 번이 8분(평소의 2배 이상)을 넘거나 GPU 전체 사용량이 11.0 GiB를 넘으면 멈추고 보고한다.

### 해석의 한계 (보고서에 그대로 적는다)

- 모방 지표(기사의 실제 수를 맞히는 정도)만 본다. 스타일 지문이나 혼동 행렬(제안서 6.3)이 아니며, 스타일이 분리됐다는 증거로 내세우지 않는다.
- 세 어댑터는 train 데이터의 양과 국면 분포가 다르다. 1단계의 val 겹침 비율과 함께 해석한다.

### 완료 기준

- 3×3 표(7개 지표), 기준선 대비 개선 표, 대각선 대비 차이와 95% 구간 표가 나온다.
- 대각선이 학습 마지막 eval과 같다.
- `mydocs/test_result/task_m100_6_test.md`에 실행 기록을 남긴다.

## 3단계: 실행 가이드 갱신, 종합 문서 완성

### 실행 가이드 (`mydocs/manual/training_guide.md`) 갱신 항목

| 절 | 내용 |
|------|------|
| 6. 학습 | 136M 본 학습의 실측: 시간(3.1~3.6시간, 평가 포함), 처리량, `max_memory_gib`, GPU 전체 사용량. 기본값 표의 `--eval-every`(500)와 본 학습에 쓴 1000의 차이 |
| 6. 학습 (신규 소절) "학습 중 평가와 GPU 메모리" | 학습 뒤 평가가 예약 메모리를 키워 WSL에서 넘치면 극단적으로 느려진 사례(카르포프), 대책 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`(스미슬로프, 결과 동일 확인). 환경변수는 `config.json`에 남지 않으므로 실행 기록에 적는다 |
| 중단과 재개 | 자동 재시도 스크립트 운영 방식. 중단 지점은 실행 로그에서 실패한 시도의 마지막 train 줄로 적는다. Task #5 이력(정정 표시로 이미 반영)은 짧게 정리 |
| CUDA 오류 기술 | 세 학습의 이력으로 갱신 (탈 3회, 스미슬로프 1회, 카르포프 없음. 카르포프의 종료 코드 137은 다른 원인) |
| 7. 결과 저장 | 실제로 해 온 방식(`mydocs/test_result/task_m{N}_{번호}_test.md`, 실행 로그·GPU 기록 위치, 환경변수 기록)에 맞춘다 |

- 가이드는 현재 코드 기준으로 쓴다.
- 갱신 전 가이드 전체를 읽고, 바꾼 곳의 목록을 단계 보고서에 남긴다.

### 종합 문서 완성

- `mydocs/tech/adapters_136M_summary.md`에 요약, 조건 차이, 한계, 다음 단계(스타일 특성·α 스윕)가 기댈 수치를 정리해 완성한다.

### 완료 기준

- 가이드의 기술이 세 학습의 기록과 어긋나지 않는다 (가이드의 수치마다 출처를 단계 보고서에 표로 남긴다).
- 종합 문서의 수치가 1·2단계 스크립트 출력과 같다.

## 위험과 대응

| 위험 | 대응 |
|------|------|
| 교차 평가 중 GPU 메모리 넘침·평가 지연 | `expandable_segments:True`, 어댑터마다 새 프로세스, 멈출 기준 |
| 대국별 `evaluate` 호출이 느림 (대국 수백 번 호출) | 먼저 한 val로 시간을 재고, 전체 평가보다 1.5배 넘게 느리면 대국 묶음을 배치로 모아 한 번에 평가하고 묶음 경계만 기록하는 방식으로 바꾼다 (결과는 같다) |
| 교차 평가 결과가 기대와 다름 (대각선이 가장 좋지 않음) | 그대로 보고한다. val 겹침과 데이터 양을 함께 적는다 |
