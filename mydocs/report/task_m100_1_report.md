# Task #1 최종 결과보고서: 기사별 기보(PGN) 전처리 및 LoRA 파인튜닝 학습 코드 작성

## 개요

탈·카르포프·스미슬로프의 기보를 국면 단위 학습 데이터로 전처리하는 코드, searchless_chess action-value Transformer의 PyTorch 이식, 그 위에 기사별 LoRA 어댑터를 학습하는 코드를 작성했다. 이식 모델은 원본 JAX 출력과 수치적으로 일치함을 9M·136M·270M 세 크기에서 확인했고, 학습 코드는 로컬 GPU(RTX 4070 Ti 12GB)에서 136M으로 짧은 학습까지 돌려 동작을 확인했다. 세 기사 전체 데이터에 대한 본 학습은 이 타스크의 범위 밖이며 아직 하지 않았다.

python -m src.model.convert --params base_model/270M_params.npz --size 270M --out base_model/270M.pt

FEN 77토큰화, 1,968 행동 공간, 모델 본체, Haiku 체크포인트 변환. 변환된 `9M.pt`, `136M.pt`, `270M.pt`와 기준 출력이 로컬 `base_model/`에 있다 (git 제외 대상).

### LoRA·정책·손실 (`src/model/lora.py`, `src/train/policy.py`, `src/train/losses.py`)

- LoRA: 베이스 전체 동결, 어텐션 q·k·v·o(선택적으로 MLP)에 주입, 어댑터만 저장·로드
- 정책: π(a|s) = softmax(q(s,a) / T), 합법수를 한 줄로 펴서 순전파한 뒤 국면별로 묶음
- 손실: L = L_imit + α·L_style + λ·L_strength. 모방 항(γ 가중 옵션), 기력 항 구현. 스타일 항은 인터페이스만 있고 α=0 기본값

### 학습 (`scripts/cache_base_q.py`, `src/data/dataset.py`, `src/train/train.py`)

```bash
python scripts/cache_base_q.py --player tal --base base_model/270M.pt
python -m src.train.train --player tal --base base_model/270M.pt --out runs/tal_270M
```

갱신 단위는 국면 32개이고, 합법수 128개 이하 묶음으로 나눠 기울기를 누적한다. 학습 전 베이스 기준선과 주기적인 val 지표(모방 손실, top-1/top-3 일치율, regret, 밴드 이탈률)를 `log.jsonl`에 남기고 `adapter.pt`를 저장한다.

```python
from src.model.lora import load_adapter
from src.model.transformer import load_base

model = load_base("base_model/270M.pt", "cuda")
load_adapter(model, "runs/tal_270M/adapter.pt")
```

## 발견 사항

1. **원본 체크포인트는 orbax 형식이라 numpy만으로 읽을 수 없다.** 변환을 "JAX 환경에서 npz 추출 → PyTorch 변환" 두 단계로 나눴다. 학습 코드에는 JAX 의존성이 없다. 이미 변환한 `.pt`를 복사하면 서버에 JAX 환경이 필요 없다.
2. **이식의 세부 사항은 원본 소스를 줄 단위로 대조해 확정했다.** 입력을 오른쪽으로 한 칸 미는 처리, FEN 토큰과 행동 토큰이 같은 임베딩 표를 쓰는 점, 최종 출력층에만 bias가 있는 점, 원본 엔진이 EMA가 아닌 `params`를 쓰는 점 등이다.
3. **합법수별 순전파 때문에 GPU 메모리가 학습 설계를 좌우한다.** LoRA가 모든 블록에 들어가 전 층의 활성값을 보관해야 하고, 합법수 1개당 136M 약 35 MiB, 270M 약 65 MiB가 든다. 국면 32개를 한 번에 역전파하는 원래 계획은 136M·270M에서 불가능해 기울기 누적으로 바꿨다 (2026-10-07 작업지시자 결정).
4. **한 번에 넣는 양을 키워도 빨라지지 않는다.** 처리량은 합법수 128개 이상에서 일정했고, GPU 메모리를 넘기면 수십 배 느려졌다 (WSL). 캐시와 평가의 기본 묶음 크기를 256으로 잡았다.
5. **bfloat16은 q를 평균 5e-4, 최대 1e-2~2e-2 바꾼다.** T=0.02, τ=0.02에 비해 작지 않아 캐시와 평가는 float32를 기본으로 했다. 학습의 순전파는 bfloat16이다.
6. **기력 항이 모방 항보다 훨씬 작다.** 실제 데이터에서 기력 항은 약 0.005로 모방 항(1.3~1.8)의 0.3% 수준이다. λ=1.0에서 기력 항이 실제 제약으로 작동하는지는 확인되지 않았다.
7. **카르포프 데이터의 특이점**: 이름 표기가 3종이고, 속기·다면기 계열이 1,094판으로 전체의 31%다. 이벤트명에 표기가 없어 속기 여부를 판단할 수 없는 약 107판은 작업지시자 결정으로 포함했다.
8. **소요 시간 (로컬 GPU 실측 처리량에서 계산한 추정)**: q 캐시는 세 기사 합계 136M 약 2.8시간, 270M 약 5.6시간. 136M 학습은 갱신당 약 1.3초로 세 기사 3 epoch이 약 9시간이다.

### 검증하지 않은 것

- 세 기사 전체 데이터에 대한 q 캐시 생성과 본 학습
- 카르포프·스미슬로프 데이터로의 학습, 270M으로의 학습 (270M은 메모리 사용량만 확인)
- GPU 서버에서의 실행 (모든 확인은 로컬 컨테이너에서 했다)
- 학습된 어댑터가 기사의 스타일을 실제로 반영하는지. 확인 학습은 전체의 2.5% 데이터와 val 500국면이라 일치율 변화를 판단할 수 없다
- 스타일 항 (손계산 예시로만 확인)

## 계획 대비 차이

| 항목 | 계획 | 실제 | 사유 |
|------|------|------|------|
| 단계 구성 | 1~4단계 | 0단계(환경 설정) 추가 | 작업지시자 지시 |
| 체크포인트 변환 | numpy로 직접 읽어 변환 | JAX 환경에서 npz 추출 후 변환 (2단계) | 체크포인트가 orbax 형식 |
| 이식 검증 위치 | GPU 서버에서 작업지시자가 실행 | 로컬 컨테이너에서 원본을 직접 실행해 완료 | 작업지시자 지시 |
| 로컬 환경 | GPU 없음 전제 | 컨테이너에 GPU 연결 (`torch`를 CUDA 포함 휠로 변경) | 작업지시자 승인 |
| 이벤트 필터 | 계획서의 키워드 | 실제 이벤트명 조사 후 규칙 확대 | 카르포프 81판이 빠져나감 (1단계) |
| 학습 배치 처리 | 국면 32개를 한 번에 순전파 | 합법수 한도 묶음으로 기울기 누적 | GPU 메모리 부족, 작업지시자 결정 |
| 캐시 묶음 기본값 | 1024 | 256 | 메모리 초과 시 급격히 느려짐 |
| 평가 정밀도 | 명시 없음 | float32 기본 | bfloat16이 베이스 기준선과의 비교를 흐림 |
| 4단계 GPU 확인 | GPU 서버에서 136M 짧은 학습 | 로컬 GPU에서 수행 | 로컬에 GPU가 연결됨 |

수행 계획서의 범위(전처리, 이식, LoRA, 학습 스크립트)는 모두 구현했다.

## 남은 일과 후속 과제

- **본 학습 (작업지시자 실행)**: `mydocs/manual/training_guide.md` 절차대로 q 캐시 생성 후 학습하고, 결과를 `mydocs/test_result/`에 저장한다.
- **첫 학습 결과를 보고 정할 것**: 학습률·epoch 수, λ와 τ (발견 사항 6), 학습도 float32로 할지 여부 (발견 사항 5).
- **없는 기능**: 학습 재개(resume). 장시간 학습이 중단되면 처음부터 다시 돌려야 한다.
- **후속 타스크 (범위 외, 미등록)**: 스타일 특성 벡터 f(s,a) 라벨링과 방향 벡터 w_p 추정, α 스윕과 평가.
