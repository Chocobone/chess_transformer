# Task #2 최종 결과보고서: 탈 LoRA 어댑터 본 학습 (136M)

## 개요

136M 베이스 위에 탈의 LoRA 어댑터를 3 epoch(7,455 갱신) 끝까지 학습했다. val 3,880국면에서 탈이 둔 수에 대한 imitation이 1.4369에서 1.0661로, top1이 60.6%에서 65.4%로 좋아졌고 기력 쪽 지표는 베이스 기준선보다 나빠지지 않았다. 학습이 CUDA 오류로 거듭 중단되어 학습 재개 기능을 추가했고, 세 기사의 136M 베이스 q 캐시도 이 타스크에서 만들었다.

타스크는 세 기사 학습으로 시작했으나 2026-10-12 작업지시자 지시로 범위를 탈 학습까지로 줄였다. 카르포프·스미슬로프 학습과 세 기사 결과 종합은 하지 않았고 각각 별도 이슈에서 진행한다.

## 산출물

### 탈 어댑터 (`runs/tal_136M/`, git 제외)

```bash
python -u -m src.train.train --player tal --base base_model/136M.pt \
    --out runs/tal_136M --eval-every 1000 --resume
```

rank 16, 학습률 1e-4, 3 epoch, 배치 32국면, seed 0. `adapter.pt`는 4,213,603바이트, SHA-256 `3931359e235d2f50f9aa2eb0d4f39c54fa363152f3fbc35e925e8246b5fe0b9a`. 학습 3시간 8분(중단 1회 포함), 최대 GPU 메모리 4.61 GiB.

val 3,880국면 전체:

| 지표 | 베이스 기준선 | 최종 (step 7455) | 변화 |
|---|---|---|---|
| imitation | 1.4369 | 1.0661 | −0.3708 |
| top1 | 0.6062 | 0.6539 | +0.0477 |
| top3 | 0.8688 | 0.8938 | +0.0250 |
| regret | 0.01268 | 0.00991 | −0.00277 |

### 학습 재개 기능 (`src/train/train.py`)

- `{out}/checkpoint.pt`를 평가 때마다, 그리고 `--checkpoint-every`(기본 200) 갱신마다 저장한다. LoRA 가중치, 옵티마이저·스케줄러, step, 데이터 순서와 난수 상태가 들어 있다.
- `--resume`: 체크포인트가 있으면 이어서 돌고 없으면 처음부터 시작한다. 설정이 다른 체크포인트와, `--resume` 없이 체크포인트가 있는 폴더에 쓰는 것은 거부한다.
- 재개한 학습의 어댑터와 로그는 끊기지 않은 학습과 같다 (시간 관련 값 제외).

### 베이스 q 캐시 (`data/processed/{player}/base_q_136M.npz`, git 제외)

세 기사 모두 만들었다. 합법수 합계 9,000,160개, 생성 2시간 49분. 파일별 SHA-256은 1단계 보고서에 있다. 카르포프·스미슬로프 학습에 그대로 쓴다.

### 그 밖

- PGN 경로를 `player_pgn/`으로 수정 (`src/players.py`, `tests/test_env.py`)
- 오류 시 자동 재시도 실행 스크립트 `runs/logs/train_player.sh {player}` (git 제외). 최대 10회, 체크포인트가 전진하지 못한 채 연속 3회 실패하면 멈춘다.

## 발견 사항

1. **모방 지표는 뚜렷이 좋아졌고, 개선의 대부분은 앞쪽에서 났다.** imitation은 step 1000에 이미 1.182였고 step 4000 이후로는 1.073 → 1.066이다. top1은 step 4000의 0.6549가 가장 높다.
2. **과적합 신호는 없다.** val imitation은 마지막 평가까지 내려갔다.
3. **기력 쪽 지표는 기준선보다 나빠지지 않았다.** 올라간 것은 `regret_top1`뿐이며, 어댑터의 최선수가 베이스 기준으로 평균 승률 0.29%p를 잃는다는 뜻이다. regret·band_violation이 내려간 것은 정책이 더 뾰족해졌다는 뜻이지 베이스보다 강해졌다는 뜻이 아니다.
4. **이 지표로는 어댑터가 탈의 "스타일"을 배웠는지 알 수 없다.** val에서 탈이 둔 수를 더 잘 맞힌다는 것까지만 말할 수 있다.
5. **학습 중단의 원인은 찾지 못했다.** 같은 명령·같은 seed의 실행이 네 번 중 세 번, 서로 다른 지점(1,840 / 4,000 / 4,800 갱신 부근)에서 두 종류의 CUDA 오류로 멈췄다. 중단 전까지의 기록은 실행끼리 같았고 1차 중단 구간은 다시 돌려도 재현되지 않았다. 실행 환경(GPU·드라이버·WSL2)의 불안정으로 판단하며, 카르포프·스미슬로프 학습에서도 일어날 수 있다.
6. **GPU 전체 사용량은 학습 중 7.5 GiB에서 9.98 GiB까지 늘어난다.** `max_memory_gib`는 4.61 GiB로 일정했다. 중단과의 관계는 확인하지 못했다.
7. **소요 시간은 1단계 추정과 맞았다.** 갱신당 1.33초, val 평가 1회 약 2.4분(탈). 같은 계산으로 카르포프는 약 3.9시간, 스미슬로프는 약 3.7시간이다 (추정).

## 검증

| 항목 | 결과 |
|------|------|
| 단위 테스트 | 111 passed (기존 101건 + 재개 10건) |
| q 캐시 | 세 기사 282,910국면에서 합법수 순서 불일치 0건, 둔 수 누락 0건, 무작위 200국면 재계산 최대 오차 4.6e-06 |
| 재개 동일성 (테스트) | 1·2·4회 죽였다가 재개한 학습의 어댑터와 로그가 끊기지 않은 학습과 같다 |
| 재개 동일성 (GPU, 136M 60 갱신) | 끊지 않은 실행, `kill -9` 1회, 2회의 `adapter.pt` SHA-256이 같다 |
| 수정 전 코드와의 동일성 | 수정 전 2차 실행의 기록 205줄 전체가 최종 실행과 같다 |
| 학습 완료 | 마지막 평가 step 7455 = `total_steps`, train 줄 373개에 빠짐·겹침 없음, NaN 없음 |
| 어댑터 재평가 | 새 베이스에 붙여 다시 평가한 값이 마지막 평가와 7개 지표 모두 같다 |

확인하지 못한 것:

- 재개가 실제로 일어난 구간(step 4800 이후)은 비교할 끊기지 않은 실행이 없다. 이 구간의 동일성은 테스트와 60 갱신 GPU 확인으로만 뒷받침된다.
- 중단의 원인.

## 계획 대비 차이

- **범위 축소**: 계획은 세 기사 학습(4단계)이었으나 탈 학습(2단계)까지만 했다. 카르포프·스미슬로프 학습은 기사별 이슈로, 세 기사 결과 종합과 `mydocs/manual/training_guide.md` 갱신은 별도 이슈로 옮겼다. 실행 가이드의 체크포인트·재개 사용법은 이슈를 닫은 뒤 2026-10-12에 추가했고, 소요 시간 등 나머지 갱신은 그 이슈에서 한다.
- **소스 수정**: 계획은 소스 수정 없는 실행 작업이었으나 재개 기능을 추가했다 (수행 계획서의 결정 1을 안 A에서 안 B로 변경).
- **PGN 경로 수정**을 이 타스크에 포함했다.
- **GPU 재개 확인**의 평가는 val 전체가 아니라 앞쪽 500국면으로 했다.
- **갱신 횟수**는 계획서의 7,452가 아니라 7,455다 (epoch마다 마지막의 작은 배치도 한 번의 갱신).
