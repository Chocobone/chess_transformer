# Task #4 최종 결과보고서: 스미슬로프 LoRA 어댑터 본 학습 (136M)

## 개요

136M 베이스 위에 스미슬로프의 LoRA 어댑터를 탈·카르포프와 같은 코드·같은 학습 설정으로 3 epoch(8,736 갱신) 끝까지 학습했다. val 4,753국면에서 스미슬로프가 둔 수에 대한 imitation이 1.4497에서 1.0936으로, top1이 56.4%에서 63.3%로 좋아졌다. 기력 쪽 지표는 `regret_top1`만 기준선보다 조금 올랐다.

카르포프 학습에서 문제가 됐던 평가 지연을 막기 위해 학습 전에 사전 측정을 했다. 기본 설정에서는 학습 뒤 평가가 GPU 메모리를 11.29 GiB까지 잡아 한도에 가까웠다. 그래서 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`를 대책으로 정했고, 이 설정으로 GPU 사용량이 5.57 GiB로 줄었으며 학습 결과는 바뀌지 않았다.

본 학습에서는 평가 9회가 모두 약 194초로 일정했고, 학습 구간 처리량도 떨어지지 않았다. 전체 3시간 37분으로 추정(3.6시간)과 맞았다. 중간에 CUDA 오류로 한 번 멈췄고, 자동 재개로 이어 갔다.

# → python -u -m src.train.train --player smyslov --base base_model/136M.pt \
#       --out runs/smyslov_136M --eval-every 1000 --resume

- 학습 설정: rank 16, 학습률 1e-4, 3 epoch, 배치 32국면, seed 0. `config.json`이 탈·카르포프와 다른 값은 `player`, `out`, 데이터 크기에 따른 세 값뿐이다.

## 발견 사항

1. **기본 설정이면 스미슬로프 학습도 GPU 메모리 한도에 가까웠다.** 학습만 돌 때 7.86 GiB였는데, 학습 뒤 첫 평가가 3.43 GiB를 더해 11.29 GiB가 되었다 (카드 12.0 GiB, 데스크톱 포함). 어제의 어림(11.1~11.9 GiB)과 맞는다. 60 갱신·평가 3회 동안에는 아직 넘치지 않아 평가 시간이 정상(195초)이었다.
2. **`expandable_segments:True`가 가장 효과가 컸고, 결과를 바꾸지 않았다.** 사전 측정 결과는 다음과 같다.
   - GPU 최대가 5.57 GiB였고, 평가가 시작돼도 늘지 않았다. 학습이 잡는 양도 줄었다.
   - 60 갱신 어댑터의 SHA-256과 val 지표가 기본 설정과 같았다.
   - `--eval-max-moves 128`도 기준(11.0 GiB)은 통과했다 (9.95 GiB). 다만 `config.json`이 달라지고 지표에 1e-7 수준 차이가 생긴다.
3. **본 학습에서 평가 지연이 일어나지 않았다.** 평가 9회가 모두 193~195초였고, GPU 전체 사용량은 최대 6.07 GiB였다. 카르포프에서는 평가가 8.6~38.6분 걸렸고 사용량은 11.9 GiB였다. 평가 지연이 GPU 메모리 넘침 때문이라는 어제의 추정과 맞는 결과다.
4. **학습 구간 처리량도 끝까지 정상이었다** (23.9~26.5 국면/초). 카르포프에서 처리량이 떨어지기 시작한 step 4,260을 지나서도 그대로였다. 다만 카르포프의 저하 원인을 모르므로, 대책 덕분인지는 말할 수 없다.
5. **CUDA 오류(device-side assert)가 한 번 났다.** step 5,400~5,420 사이에서 `vectorized gather kernel index out of bounds`로 멈췄다. [정정 (2026-10-15, Task #5): 중단은 step 5,580~5,600 사이 (실패한 시도의 마지막 train 줄이 step 5580), 잃은 갱신 180~199]
   - 탈 학습 때와 같은 메시지이고, 메모리 사용량은 5.8 GiB로 정상이었다.
   - 스크립트가 22초 뒤 step 5400 체크포인트에서 재개했고, 잃은 시간은 약 4분이다. [정정 (2026-10-15, Task #5): 잃은 갱신 180~199개, 잃은 시간 약 4~4.5분]
   - 이로써 세 기사 학습 중 두 기사에서 같은 오류가 났다.
6. **모방 지표는 뚜렷이 좋아졌고, 개선의 대부분은 앞쪽에서 났다.** imitation은 step 1000에 이미 1.205였다. step 6000 이후로는 1.094~1.096에서 거의 움직이지 않았다.
7. **과적합 신호는 없다.** val imitation은 step 7000에서 0.0002 올랐다가 다음 평가에서 내려왔다.
8. **기력 쪽에서 나빠진 지표는 `regret_top1`뿐이다** (+0.29%p).
   - 어댑터의 최선수가 베이스 기준으로 평균 승률 0.29%p를 잃는다는 뜻이다.
   - regret·band_violation이 내려간 것은 정책이 뾰족해졌다는 뜻이지, 베이스보다 강해졌다는 뜻이 아니다.
9. **이 지표로는 어댑터가 스미슬로프의 "스타일"을 배웠는지 알 수 없다.** 탈·카르포프와의 비교도 기준선과 val 집합이 달라 이 타스크에서 하지 않았다.

## 검증

| 항목 | 결과 |
|------|------|
| 단위 테스트 | 111 passed (1단계, 3단계) |
| 사전 확인 | 캐시 SHA-256이 Task #2 1단계 보고서 값과 일치, 소스가 `06b57fa`와 같음 |
| 대책의 영향 | 60 갱신 어댑터 SHA-256과 val 지표가 기본 설정과 같다 |
| 학습 완료 | 마지막 평가 step 8736 = `total_steps`, train 줄 437개에 빠짐·겹침 없음, NaN 없음 |
| 어댑터 재평가 | 새 베이스에 붙여 기본 할당 방식으로 다시 평가한 값이 마지막 평가와 7개 지표 모두 같다 (차이 0) |
| 탈·카르포프와 설정 동일성 | `config.json`에서 다른 값은 `player`, `out`, `total_steps`, `train_positions`, `val_positions`뿐 (환경변수는 별도로 명시) |
| 결과 문서의 수치 | 표와 로그 원문은 스크립트 출력을 그대로 넣었다 |

확인하지 못한 것:

- 재개가 일어난 뒤의 구간(step 5400 이후)이 끊기지 않은 학습과 같은지. 비교할 실행이 없고, Task #2의 테스트와 60 갱신 GPU 확인으로만 뒷받침된다.
  - **정정 (2026-10-15, Task #5)**: 같지 않았다. 수정 전 코드는 `--num-workers` > 0에서 epoch 1 이후에 재개하면 데이터 순서가 끊기지 않은 학습과 달라졌다. 스미슬로프는 step 5400(epoch 1)에서 재개해, epoch 1에서 국면 11,597개(12.45%)가 두 번, 같은 수가 한 번도 학습되지 않았다. epoch 2는 빠짐없이 학습했지만 순서가 다르다 (`mydocs/troubleshootings/resume_data_order.md`).
- CUDA 오류의 원인.
- 처리량 저하가 없었던 것이 대책 덕분인지.
- 호스트(Windows)의 공유 GPU 메모리 사용량. 이번에는 사용량이 6 GiB대라 넘칠 일이 없었다.

## 계획 대비 차이

- **대책 비교 범위**: 계획 순서대로면 (가) `--eval-max-moves 128`이 통과했으니 (나)는 재지 않아도 됐다. (가)는 `config.json`이 탈·카르포프와 달라지므로 비교를 위해 (나)도 쟀다 (11분 추가). 결정은 (나)였다.
- **학습 중 중단 1회**: 계획의 리스크 항목대로 자동 재개에 맡겼다. 멈출 기준에는 닿지 않았다.
- **소요 시간**: 추정(사전 측정 뒤 재계산) 약 3.6시간, 실제 3시간 37분.

## 후속 작업

- **세 기사 결과 종합, 실행 가이드 갱신** (별도 이슈). 이번 타스크에서 정리된 것:
  - 학습 중 평가 시간 추정이 맞지 않을 수 있다는 점과 그 원인(평가의 예약 메모리), 대책(`expandable_segments:True`)을 가이드에 반영한다.
  - 대책을 기본으로 하려면 `train_player.sh`나 가이드의 실행 명령에 환경변수를 넣고, `config.json`에 남지 않는 문제를 어떻게 기록할지 정한다.
  - 탈·카르포프는 환경변수 없이, 스미슬로프는 환경변수와 함께 학습했다. 1단계 대조로 학습 계산은 같다고 확인했지만, 종합할 때 이 차이를 적어 둔다.
- **CUDA 오류(device-side assert)**: 세 기사 중 두 기사에서 났다. 자동 재개로 대응은 되지만, 원인 조사를 별도 이슈로 할지 정해야 한다.
