# Task #5 최종 결과보고서: 학습 재개 시 데이터 순서 불일치 수정, 학습 기록 정정

## 개요

원래 오늘의 과제는 탈·스미슬로프 학습을 멈춘 CUDA 오류(device-side assert)의 원인 조사였다. 로그를 보던 중 두 가지를 확인했다.

- 오류가 나면 프로세스가 끝나고, 실행 스크립트가 마지막 체크포인트부터 다시 시작한다. 그래서 오류가 가중치를 오염시키지는 않는다.
- 대신 자동 재개 과정에서 데이터 순서가 끊기지 않은 학습과 달라지는 결함이 있었다.

그래서 작업지시자 결정으로 범위를 이 결함의 수정과 그동안의 학습 기록 정정으로 바꿨다. 체크포인트로 CUDA 오류를 재현하는 원인 조사와, 성능 영향 실측은 하지 않았다.

결함의 원인은 `DataLoader`가 데이터 순서용 생성기에서 worker 시드까지 뽑았다는 것이다. `num_workers=2`(본 학습 설정)에서 epoch 1 이후에 재개하면 순열이 밀렸다. worker 시드용 생성기를 따로 두어 고쳤고, 수정 전 방식의 체크포인트로는 끝나지 않은 학습을 잇지 않게 했다.

이 결함으로 탈·카르포프·스미슬로프 136M 어댑터 모두, 재개한 epoch에서 일부 국면을 두 번 학습하고 같은 양을 한 번도 학습하지 않았다. 비율은 0.83~12.45%다. 또 스미슬로프와 탈의 중단 지점이 기존 기록과 달랐다. Task #2~#4 문서 14개, 28곳을 정정했다.

## 원인

`src/train/train.py`는 생성기 하나를 `RandomSampler`와 `DataLoader(generator=...)`에 함께 넘겼다. `DataLoader`는 반복자를 만들 때마다 이 생성기에서 worker 시드를 뽑는다.

- `num_workers=2`에서는 `persistent_workers=True`라 반복자를 처음 한 번만 만든다. 그래서 epoch 1부터는 순열만 뽑는다.
- 재개한 프로세스는 epoch 시작 때의 생성기 상태를 복원한 뒤 반복자를 새로 만들면서 시드를 한 번 더 뽑는다. 그 결과 재개한 epoch의 나머지와 그 뒤 epoch 전체의 순서가 끊기지 않은 학습과 달라진다.
- 기존 재개 테스트는 `--num-workers 0`으로만 돌았다. Task #2의 GPU 재개 확인은 epoch 0 안에서만 끊었다. 그래서 둘 다 이 결함을 잡지 못했다.

근거는 두 가지다.

- 실행 로그에서 실패한 시도와 재개한 시도의 같은 step을 비교하면 lr은 같고 loss는 첫 기록부터 다르다. 예를 들어 스미슬로프 step 5420에서 1.4239와 1.0175, 탈 step 4820에서 0.7709와 0.9388이다.
- 실제 `DataLoader`를 쓴 CPU 시뮬레이션에서 `num_workers=0`이면 순서가 같고 `2`면 달랐다.

## 세 어댑터가 받은 영향 (수정 전 코드, 추정)

| 기사 | 재개 | 재개한 epoch에서 2회 / 0회 학습된 국면 | 3 epoch 합계 횟수 분포 (계획은 모두 3회) |
|------|------|------|------|
| 탈 | step 4800 (epoch 1) | epoch 1: 5,045 / 5,045 (6.35%) | 2회 5,045 · 3회 69,403 · 4회 5,045 |
| 카르포프 | step 6000 (epoch 1), 6200 (epoch 2) | epoch 1: 801 / 801 (0.83%), epoch 2: 5,279 / 5,279 (5.48%) | 1회 52 · 2회 5,895 · 3회 84,487 · 4회 5,919 · 5회 40 |
| 스미슬로프 | step 5400 (epoch 1) | epoch 1: 11,597 / 11,597 (12.45%) | 2회 11,597 · 3회 69,984 · 4회 11,597 |

- 갱신 수, 학습률 일정, 학습한 국면의 총량은 계획과 같다. 달라진 것은 국면별 학습 횟수와 배치 순서다.
- 성능 영향은 실측하지 않았다. 재개 뒤에도 val 지표는 계속 좋아졌다.
- 세 어댑터는 "같은 조건으로 끊기지 않고 학습한 결과"가 아니다. 세 기사를 종합할 때 이 차이를 적어야 한다.

## 수정 (`src/train/train.py`)

- worker 시드용 생성기 `worker_seeds`를 따로 둔다. 순서용 `generator`는 샘플러만 쓴다. 데이터 처리에 난수가 없으므로 worker 시드는 결과에 영향이 없다.
- 체크포인트에 `"data_order": 2`를 넣는다. 표시가 없는 체크포인트로 끝나지 않은 학습을 재개하면 `ValueError`로 거부한다. 이미 끝난 학습은 갱신 없이 끝난다.
- 부작용: epoch 0부터 순서가 수정 전과 다르다. 따라서 수정 전 어댑터의 배치 순서는 재현할 수 없다 (승인된 단점).
- 같은 소형 학습을 수정 전·후로 비교하면 baseline, step·epoch·lr, epoch별 학습 국면 집합은 같고 배치 순서만 다르다.

## 남은 일과 한계

- **CUDA 오류(device-side assert)의 원인은 밝히지 않았다.** 체크포인트 재현을 하지 않기로 했다. 오류가 나도 가중치는 오염되지 않고, 이제 재개가 끊기지 않은 학습과 같은 결과를 낸다. 그래서 오류가 다시 나도 결과에는 영향이 없다. 보류로 이월한다.
- 영향 추정은 순서 관련 루프를 옮긴 시뮬레이션이다. 실제 배치 내용은 로그에 없어 직접 대조하지 못했다.
- 성능 영향 실측과 세 어댑터의 재학습은 하지 않았다. 재학습하면 수정된 코드의 순서(epoch 0부터 다름)로 돌게 된다.
- 다음 이슈(세 기사 결과 종합, 실행 가이드 갱신)에서 세 어댑터의 학습 조건 차이를 반영해야 한다. 차이는 두 가지다: 재개 구간의 순서(이번 타스크), 그리고 스미슬로프만 `expandable_segments` 환경변수를 썼다는 점(Task #4).
