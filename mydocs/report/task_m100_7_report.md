# Task #7 최종 결과보고서: 모델과 사용자가 직접 대국하는 체스 앱 개발 (유저 확인용)

## 개요

학습한 모델(베이스 9M·136M·270M, 136M 기사 어댑터 탈·카르포프·스미슬로프)과 사용자가 브라우저에서 직접 두는 로컬 대국 앱을 만들었다. 모델은 학습과 같은 정책 π(a|s) = softmax(q / 0.02)에서 수를 샘플링한다. 화면에는 모델이 고려한 후보 수와 확률이 나오고, 같은 국면에서 네 모델의 후보를 나란히 보는 비교 패널도 있다.

구성은 세 층이다. 웹과 무관한 추론 엔진(`src/play/engine.py`), FastAPI 서버(`game.py`, `server.py`), 프레임워크 없는 HTML·CSS·JS 화면(`src/play/static/`)이다. 실제 가중치로 응답 시간과 GPU 메모리를 쟀다. 136M 모델 수는 중앙값 41.5~56.9 ms다. 작업지시자가 탈(136M)과 한 판을 체크메이트까지 두어 동작을 확인했다.

### 실기 대국

작업지시자(백)와 탈(136M)이 둔 대국은 1-0, 57. Qfh7#로 끝났다. 승진 창, 체크메이트 종료 판정, PGN 저장, 퀸이 여럿일 때의 SAN 구분 표기가 정상 동작했다. 내려받은 PGN은 python-chess로 다시 읽어 113플라이 모두 합법임을 확인했다. 이상 동작 보고는 없었다.

## 발견 사항

1. **`board.outcome(claim_draw=True)`는 3회 반복을 미리 판정한다**: 다음 한 수로 3회 반복이 *될 수 있기만 해도* 무승부로 본다. 같은 국면이 실제로 세 번 나왔을 때만 끝내려고 `is_repetition(3)`과 `is_fifty_moves()`를 직접 검사하도록 바꿨다 (2단계).
2. **어댑터 전환 비용은 무시할 만하다**: LoRA 가중치만 바꿔 끼우므로 136M 안의 모델 전환에 드는 시간이 측정 잡음 안에 든다. 그래서 비교 패널(모델 4개)이 순전파 4회 시간과 거의 같다.
3. **불러오는 동안 GPU 최대 사용량은 상주량의 약 2배다**: 가중치가 잠시 두 벌 있기 때문이다. 서버를 오래 쓰면 PyTorch 캐시가 커져 136M 앱 몫이 최대 2.3 GiB까지 오른다.
4. **모델 기력**: 실기 대국에서 탈(136M)은 초반에 룩 두 개를 잃었다. 탐색 없이 T = 0.02로 샘플링하는 정책이라 전술 수읽기에 약한 것으로 보인다. 앱 결함은 아니다. 후속 평가(제안서 6장 대국 성적)에서 다룰 사항이다.

## 알려진 한계

- 모델은 FEN만 보고 수의 이력은 보지 않는다. 이긴 국면에서도 3회 반복으로 비기는 수를 둘 수 있다. 앱은 반복을 만든 수를 기보에 표시한다.
- π 샘플링은 확률이 낮은 수도 가끔 고른다 (의도한 동작). 기보의 π 표시로 알 수 있다.
- 한 사용자, 한 대국만 서버 메모리에 둔다. 서버를 다시 띄우면 대국이 사라진다.
- 화면 코드는 자동 테스트가 없다. 실기 확인으로 대신했다.
