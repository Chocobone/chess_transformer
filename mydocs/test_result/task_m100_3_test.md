### 이 지표로 말할 수 있는 것과 없는 것

- val에서 카르포프가 둔 수를 베이스보다 잘 맞힌다 (imitation −0.343, top1 +4.7%p). 개선의 대부분은 앞쪽에서 났고 step 6000 이후로는 imitation이 1.151~1.153에서 움직이지 않았다.
- val imitation이 다시 오르는 과적합 신호는 없다. step 7000에서 1.1535로 조금 올랐다가 다음 평가에서 1.1515로 내려왔다.
- 기준선보다 나빠진 지표는 `regret_top1`뿐이다. 어댑터의 최선수가 베이스 기준으로 평균 승률 0.27%p를 잃는다는 뜻이다. regret·band_violation이 내려간 것은 정책이 더 뾰족해졌다는 뜻이지 베이스보다 강해졌다는 뜻이 아니다.
- 어댑터가 카르포프의 "스타일"을 배웠는지는 이 지표로 알 수 없다.
- 탈의 결과와는 여기서 비교하지 않는다. 기준선과 val 집합이 달라 수치를 나란히 놓는 것만으로는 판단할 수 없고, 세 기사 종합은 별도 이슈에서 한다.

### 확인

- 마지막 `eval`의 step(9039)이 `config.json`의 `total_steps`(9039)와 같다.
- `train` 줄 452개의 step이 20, 40, …, 9020, 9039로 빠짐·겹침이 없다 (재개 지점 두 곳 포함).
- 저장된 `adapter.pt`를 새로 올린 베이스에 `load_adapter`로 붙여 val 전체를 다시 평가한 값이 마지막 `eval`의 7개 지표와 모두 같다 (차이 0). 아래 "평가 단독 측정"의 카르포프 실행이 이 재평가다.
- 재개가 일어난 뒤의 구간(step 6000 이후)은 비교할 끊기지 않은 실행이 없다.
  - **정정 (2026-10-15, Task #5)**: 같지 않았다. 수정 전 코드는 `--num-workers` > 0에서 epoch 1 이후에 재개하면 데이터 순서가 끊기지 않은 학습과 달라졌다. 카르포프는 step 6000(epoch 1)과 6200(epoch 2)에서 재개해, epoch 1에서 국면 801개(0.83%), epoch 2에서 5,279개(5.48%)가 두 번, 같은 수가 한 번도 학습되지 않았다 (`mydocs/troubleshootings/resume_data_order.md`).

| 평가가 더한 양 | 5.68 GiB | 8.18 GiB | 3.92 GiB |
| 온도, 전력 | 62~72℃, 약 275W | 61~72℃, 약 278W | 67~73℃, 약 280W |

- 예약 메모리가 늘어난 시점: 순전파 0 (합법수 248) → 2.69 GiB, 2 (250) → 3.60, 5 (254) → 4.52, 26 (256) → 5.45. 묶음 크기의 최댓값이 바뀐 네 번과 정확히 같다.
- 처리량은 처음부터 끝까지 일정했다 (구간별 772~779 수/초).
- 지표는 캐시의 베이스 q로 계산한 기준선과 같다 (최대 차이 2.8e-09, top1·top3는 차이 0). 스미슬로프의 베이스 기준선은 imitation 1.4497, top1 0.5639, top3 0.8515다.

세 기사를 놓고 보면 최댓값이 바뀐 횟수(탈 3, 스미슬로프 4, 카르포프 7)와 예약 메모리(3.70 / 5.45 / 7.95 GiB)의 순서가 같다. 늘어날 때마다의 증가분은 세 기사 모두 0.85~1.01 GiB다.

**스미슬로프 학습에 대한 함의**: 스미슬로프 평가가 잡는 양은 탈과 카르포프의 중간이다. 학습 중에 12 GiB를 넘을지는 이 측정만으로는 판단할 수 없다. 탈 학습에서는 단독 평가가 더한 양(3.92 GiB)보다 적은 약 2.6 GiB만 학습 위에 더해졌다 (7.1 → 9.7 GiB, 데스크톱 제외. [정정 (2026-10-15, Task #6): 9.7은 (9,983 − 281) MiB ÷ 1000 값으로 보인다. ÷1024로는 9.47 GiB. 7.1의 출처는 확인하지 못했다] 학습이 잡아 둔 블록을 일부 다시 쓰는 것으로 보인다). 같은 비율을 스미슬로프에 적용하면 학습 프로세스가 약 10.8 GiB, 데스크톱 사용량(0.3~1.0 GiB)을 더해 11.1~11.9 GiB [정정 (2026-10-15, Task #6): 이 어림의 입력 일부(탈의 GPU 전체 사용량)는 MiB÷1000 값이다. 실제 값은 Task #4 사전 측정에서 11.29 GiB(11,558 MiB, ÷1024)로 확인했다]로, 카드의 12.0 GiB에 거의 닿는다. 이 계산은 탈 한 번의 관찰에서 뽑은 비율에 기댄 어림이라 근거가 약하다. 여유가 없다는 것까지만 말할 수 있다.

### 해석

- **평가만 따로 돌리면 정상 속도다.** 카르포프 216초는 캐시 생성 때의 190초와 비슷하다 (측정용 동기화와 LoRA 계산이 더해진 값). 학습 중의 517~2,300초는 카르포프 val 데이터나 평가 계산 자체의 문제가 아니다.
- **평가가 예약하는 메모리가 기사마다 크게 다르다.** 실제로 쓰는 양(최대 1.68 GiB)은 같은데 카르포프는 7.95 GiB, 탈은 3.70 GiB를 잡는다. 묶음 크기가 조금씩 커질 때마다 앞서 잡아 둔 블록을 다시 쓰지 못하고 약 0.9 GiB씩 새로 잡는 것으로 보인다. 카르포프 val은 앞쪽 묶음의 크기가 일곱 단계로 올라가고 탈은 두 단계로 올라간다. (새로 잡는 이유가 PyTorch 메모리 할당기의 동작이라는 것은 추정이다. 관찰한 것은 시점의 일치다.)
- **학습 중에는 이 예약이 학습이 잡은 메모리 위에 더해진다.** 학습만 돌 때 GPU 전체 사용량은 8.2 GiB였고, 카르포프 평가가 그 위에 수 GiB를 더 잡으면 12 GiB를 넘는다. 실제로 첫 평가에서 11.9 GiB가 되었다. 탈은 평가가 잡는 양이 작아 최대 9.98 GiB에 머물렀다. [정정 (2026-10-15, Task #6): ÷1024로 카르포프 11.5~11.7 GiB (11,788~11,965 MiB), 탈 9.75 GiB (9,983 MiB). 학습만 돌 때 8.2 GiB는 8.01 GiB (8,200 MiB)] 넘친 뒤에 느려진다는 것(전용 메모리 밖으로 밀려남)은 온도·전력 하락과 맞지만 직접 확인하지는 못했다.

### 확인하지 못한 것

- 학습 뒤에 평가가 이어지는 상황을 직접 재현해 예약 메모리를 재지는 않았다. 위의 설명은 단독 측정과 학습 때의 `nvidia-smi` 기록을 이어 붙인 것이다.
- 학습 구간의 처리량이 step 4,260부터 떨어진 이유, 평가 시간이 뒤로 갈수록 늘어난 이유, 첫 재시작이 효과가 없었던 이유.
- 호스트(Windows)에서 공유 GPU 메모리가 실제로 쓰였는지.
- 대책(평가 전후 예약 메모리 비우기, `--eval-max-moves` 조정, 할당 방식 환경변수)의 효과. 이 타스크의 범위 밖이다.
