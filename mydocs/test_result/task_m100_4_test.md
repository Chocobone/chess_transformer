### 해석

- **기본 설정이면 스미슬로프 학습은 한도에 가깝다.** 학습 위에 첫 평가가 3,512 MiB(3.43 GiB)를 더해 11.29 GiB가 되었다. 카드는 12,282 MiB이므로 데스크톱 사용량이 지금(0.7~0.8 GiB)보다 0.7 GiB쯤 늘면 넘친다. 평가 3회 동안 더 오르지는 않았고, 평가 시간도 정상(195초)이었다. 아직 넘치지 않았기 때문으로 보인다.
- 어제의 어림(학습 중 11.1~11.9 GiB)과 맞는다. [정정 (2026-10-15, Task #6): 이 어림의 입력 일부(탈의 GPU 전체 사용량)는 MiB÷1000 값이다. 실제 값은 Task #4 사전 측정에서 11.29 GiB(11,558 MiB, ÷1024)로 확인했다] 학습만 돌 때 데스크톱을 뺀 양(8,046 − 791 = 7,255 MiB)은 카르포프(8,209 − 1,034 = 7,175 MiB)와 거의 같다.
- **`--eval-max-moves 128`은 1,248 MiB(1.22 GiB)를 줄인다** (데스크톱 제외 10,767 → 9,519 MiB). 평가 시간은 그대로다.
- **`expandable_segments:True`는 학습 쪽까지 줄인다.** 학습만 돌 때 데스크톱을 뺀 양이 7,255 → 5,027 MiB가 되었고, 평가가 시작돼도 늘지 않았다. 평가와 학습의 시간, 지표, 어댑터가 모두 그대로다. 예약 메모리가 블록을 새로 잡는 대신 늘려 쓰는 방식이라 앞서 본 "묶음 크기 최댓값이 바뀔 때마다 0.9 GiB씩 새로 잡는" 현상이 없어진 것으로 보인다 (관찰한 것은 사용량이고 할당기 내부는 보지 않았다).
- 이 환경(WSL2)에서 `expandable_segments`가 경고 없이 동작했다.

### 확인하지 못한 것

- 60 갱신·평가 3회 너머의 누적. 카르포프에서는 평가 시간이 뒤로 갈수록 늘었다 (8.6 → 38.6분). 본 학습의 감시와 멈출 기준으로 대응한다.
- `expandable_segments`가 카르포프 step 4,260부터의 학습 처리량 저하에도 듣는지. 원인을 모르므로 알 수 없다.

```bash

    setsid nohup bash -c 'echo "=== PYTORCH_CUDA_ALLOC_CONF=$PYTORCH_CUDA_ALLOC_CONF"; exec runs/logs/train_player.sh smyslov' \
```


### 이 지표로 말할 수 있는 것과 없는 것

- val에서 스미슬로프가 둔 수를 베이스보다 잘 맞힌다 (imitation −0.356, top1 +7.0%p, top3 +3.9%p). 개선의 대부분은 앞쪽에서 났고, step 6000 이후 imitation은 1.094~1.096에서 거의 움직이지 않았다.
- val imitation이 다시 오르는 과적합 신호는 없다. step 7000에서 1.0956으로 0.0002 올랐다가 다음 평가에서 1.0936으로 내려왔다.
- 기준선보다 나빠진 지표는 `regret_top1`뿐이다. 어댑터의 최선수가 베이스 기준으로 평균 승률 0.29%p를 잃는다는 뜻이다. regret·band_violation이 내려간 것은 정책이 더 뾰족해졌다는 뜻이지, 베이스보다 강해졌다는 뜻이 아니다.
- 어댑터가 스미슬로프의 "스타일"을 배웠는지는 이 지표로 알 수 없다.
- 탈·카르포프의 결과와는 여기서 비교하지 않는다. 기준선과 val 집합이 달라 수치를 나란히 놓는 것만으로는 판단할 수 없고, 세 기사 종합은 별도 이슈에서 한다.
