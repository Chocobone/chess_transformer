# Task #1 단계3 완료 보고서: LoRA 어댑터 및 손실함수

## 수행 내용

동결 베이스에 LoRA를 주입하는 모듈, 합법수별 q로 정책을 만드는 모듈, 모방 항·기력 항·스타일 항 손실함수를 구현 계획서대로 작성했다. 단위 테스트를 추가했고, 변환된 실제 가중치(9M·136M·270M)를 GPU에 올려 주입과 짧은 학습이 동작함을 확인했다.

## 구현 요약

- **LoRA**: `W x + (alpha / r) · B A x`. A는 Kaiming 균등 초기화, B는 0. `inject_lora`는 모델 전체를 동결한 뒤 블록마다 대상 선형층을 감싼다. 기본 대상은 어텐션 q·k·v·o이고 `"mlp"`를 넣으면 MLP 선형층 3개에도 주입한다. 알 수 없는 대상 이름과 이중 주입은 오류로 막는다.
- **어댑터 저장·로드**: `lora_state_dict`는 A/B만 담는다. `load_lora`는 키가 하나라도 누락되거나 남으면 실패한다 (rank나 대상이 다른 어댑터를 조용히 싣지 않도록).
- **정책**: 한 배치의 모든 합법수를 한 줄로 펴서 순전파 1회로 처리하고, `owner`로 국면별 `[B, A_max]`로 다시 묶는다. 패딩 자리는 log 확률 −∞(확률 0)이다. 수의 순서는 2단계와 같은 행동 번호 순이다.
- **손실**: 계획서의 수식 그대로다. 세 항 모두 국면 평균을 돌려준다. `total_loss`는 전체 손실과 항별 값(로그용)을 함께 돌려준다.

## 계획서 대비 추가·변경

계획서의 함수 시그니처는 그대로 두고 아래 두 함수를 `policy.py`에 추가했다.

- `pad_by_owner(values, owner, fill)`: 한 줄로 편 값을 국면별로 묶는 공통 함수. 베이스 q(기력 항 입력)도 정책과 같은 방식으로 묶어야 해서 분리했다.
- `target_index(action_ids, owner, target_actions)`: 기사가 둔 수가 그 국면의 합법수 중 몇 번째인지 구한다. 목표 수가 합법수에 없으면 오류를 낸다.

그 밖의 결정:

- 합법수가 없는 국면(체크메이트·스테일메이트)이 들어오면 `legal_action_tokens`가 오류를 낸다. 전처리 데이터는 "기사가 수를 둔 국면"만 담으므로 정상 데이터에서는 발생하지 않는다.
- 모방 항의 γ 가중치는 그래프에서 분리한다 (가중치 자체는 학습 대상이 아니다). 평균은 국면 수로 나눈다 (가중치 합으로 정규화하지 않는다).

## 발견 사항

1. **GPU 메모리: 계획서의 배치 크기(국면 32개)는 현재 구조로는 136M·270M에서 불가능하다.** LoRA가 모든 블록에 들어가므로 역전파를 위해 전 층의 활성값을 보관해야 하고, 그 양이 합법수 개수 × 79토큰에 비례한다. 로컬 GPU(RTX 4070 Ti, 12GB)에서 bfloat16 혼합 정밀도로 측정한 값은 다음과 같다.

   | 모델 | 국면/배치 | 합법수/배치 | 최대 GPU 메모리 | 스텝 시간 |
   |------|-----------|-------------|-----------------|-----------|
   | 9M | 8 | 215~316 | 2.44 GiB | 71 ms |
   | 9M | 32 | 610~1,325 | 9.99 GiB | 528 ms |
   | 136M | 2 | 42~69 | 2.83 GiB | 82 ms |
   | 136M | 4 | 96~133 | 4.73 GiB | 153 ms |
   | 136M | 8 | 215~316 | 10.15 GiB | 2,768 ms (한계 근처에서 급격히 느려짐) |
   | 136M | 32 | 610~1,325 | 메모리 부족으로 실패 | — |
   | 270M | 2 | 42~69 | 5.52 GiB | 152 ms |
   | 270M | 4 | 96~133 | 9.21 GiB | 347 ms |
   | 270M | 32 | 610~1,325 | 메모리 부족으로 실패 | — |

   합법수 1개당 136M은 약 35 MiB, 270M은 약 65 MiB가 든다. 이 비율이면 270M에서 국면 32개(합법수 약 1,000~1,300개)는 65~85 GiB가 필요해 일반적인 단일 GPU에 들어가지 않는다 (추정치이며 실측은 위 표까지다). 3단계 코드 자체의 문제는 아니고 4단계 학습 루프 설계에서 풀어야 한다. 방안은 아래 "4단계에 대한 제안"에 적었다.
2. **합법수 개수의 편차가 크다**: 같은 국면 32개라도 배치에 따라 합법수가 610~1,325개로 두 배 넘게 차이 난다. 메모리 한도는 국면 수가 아니라 합법수 수로 잡아야 안전하다.
3. **기력 항의 크기**: 실제 데이터에서 τ=0.02, T=0.02일 때 베이스 정책의 기력 항은 0.003~0.009로 모방 항(1.3~2.1)보다 두세 자릿수 작다. λ=1.0에서는 기력 항이 학습에 거의 영향을 주지 않을 수 있다. 하이퍼파라미터 조정은 4단계 첫 학습 결과를 보고 판단할 사항이라 기본값은 바꾸지 않았다.

## 검증

- `pytest`: 85 passed, 0 failed (환경 6 + 전처리 38 + 모델 23 + LoRA 7 + 손실 11)
  - LoRA 주입 직후 출력이 베이스와 완전히 동일 (`torch.equal`)
  - 학습 가능한 파라미터가 LoRA의 A/B뿐이고 개수가 기대값과 일치, 역전파 한 스텝 후 베이스 가중치 전부 불변이고 어댑터는 변함
  - 대상 선택(q·v만, MLP 포함), 잘못된 대상·이중 주입 오류
  - 어댑터 저장 → 새 모델에 로드 → 출력 동일, 키가 어긋난 어댑터는 로드 실패
  - dropout은 학습 모드에서만 작동
  - 합법수 펼치기: 국면별 개수(20·3·27), 행동 번호 순 정렬, python-chess 합법수 집합과 일치
  - 정책: 국면별 합 1, 패딩 위치 확률 0, 손계산 값과 일치
  - 모방 항: 손계산 값과 일치 (γ=0, 1, 2)
  - 기력 항: 모든 수가 밴드 안이면 0, 밴드 밖 수에 확률이 실리면 손계산 값과 일치, 패딩 자리의 q는 무시
  - 스타일 항: 특성 없으면 0, 손계산 값과 일치
  - 전체 손실이 항별 값의 가중합과 일치, 패딩이 있어도 기울기가 유한
  - 소형 무작위 모델에서 같은 배치 60회 반복 학습 시 모방 손실이 처음의 절반 미만으로 감소
- **실제 가중치 확인** (GPU, 탈 train 앞 국면, rank 16, 임시 스크립트로 실행했고 저장소에는 넣지 않았다):
  - 주입 직후 q 최대 차이: 9M·136M·270M 모두 0
  - LoRA 파라미터 수 (rank 16, q·k·v·o): 9M 262,144개, 136M 1,048,576개, 270M 2,097,152개
  - 같은 4개 배치를 돌려가며 24~40스텝 학습 시 손실이 유한하고 감소 (예: 9M 국면 32개 모방 손실 1.58 → 1.07, 270M 국면 4개 1.71 → 0.91)

### 검증의 한계

- 실제 가중치 학습 확인은 국면 8~128개를 반복해서 본 것이라 "코드가 돌아가고 손실이 내려간다"는 것만 보여 준다. val 지표로 본 일반화는 4단계에서 측정한다.
- 스타일 항은 손계산 예시로만 확인했다. 실제 특성 벡터는 이번 타스크 범위 밖이다.
- 위 메모리 표는 로컬 12GB GPU 한 대에서 잰 값이다. 한계 근처 값(136M 국면 8개)은 스텝 시간이 비정상적으로 길어 그대로 쓸 수 있는 설정이 아니다.

## 4단계에 대한 제안

**결정 (2026-10-07 작업지시자): 1번 기울기 누적으로 진행한다.** 구현 계획서 4단계에 반영한다.

구현 계획서 4단계는 `--batch-positions 32`를 한 번의 순전파로 처리한다고 가정했다. 위 측정대로라면 그대로는 실행할 수 없으므로, 4단계 착수 전에 아래 중 방향을 정해야 한다.

1. **기울기 누적 (권장)**: 유효 배치는 국면 32개로 유지하되, 합법수 개수 한도(`--max-moves-per-forward`, 예: 128)로 나눈 작은 묶음을 차례로 순전파·역전파하고 32개가 찰 때마다 한 번 갱신한다. 코드 변경이 작고 결과가 큰 배치와 수학적으로 같다. 스텝 시간은 묶음 수만큼 늘어난다.
2. **gradient checkpointing 병행**: 블록 단위로 활성값을 버리고 역전파 때 다시 계산한다. 메모리는 크게 줄지만 스텝당 계산이 늘고 `transformer.py`에 옵션이 추가된다.
3. **배치 크기만 축소**: 가장 단순하지만 갱신당 국면 수가 줄어 학습이 불안정해질 수 있다.

GPU 서버의 메모리 용량을 알려주시면 한도 기본값을 그에 맞춰 잡겠다.
