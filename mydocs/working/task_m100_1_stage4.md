# Task #1 단계4 완료 보고서: 학습 스크립트 및 GPU 서버 실행 가이드

## 수행 내용

베이스 q 캐시 스크립트, 학습용 데이터셋, 기울기 누적을 쓰는 학습 스크립트, GPU 서버 실행 가이드를 작성했다. 단위 테스트를 추가했고, CPU에서 전체 파이프라인을 완주시켰으며, 로컬 GPU(RTX 4070 Ti 12GB)에서 136M으로 짧은 학습을 돌려 손실 감소와 val 지표 출력을 확인했다.

## 구현 요약

- **q 캐시**: split마다 `offsets`, `actions`, `q` 세 배열을 저장한다. 수 순서는 `policy.py`와 같은 행동 번호 순이다. 데이터셋을 열 때 국면 수를, 배치를 묶을 때 합법수 순서를 캐시와 대조해 어긋나면 오류를 낸다 (전처리를 다시 하고 캐시를 갱신하지 않은 경우를 잡는다).
- **기울기 누적**: `split_by_moves`가 배치를 합법수 한도 이하 묶음으로 나누고, `accumulate_gradients`가 묶음마다 `손실 × (묶음 국면 수 / 배치 국면 수)`를 역전파한다. clipping·갱신·스케줄은 갱신 단위로 한 번씩 한다. 3단계 손실함수는 고치지 않았다.
- **평가**: val에서 모방 손실, top-1/top-3 일치율, regret(정책 기댓값·최선수), 밴드 이탈률, 기력 항을 잰다. 학습 전에 같은 지표를 캐시의 베이스 q로 계산해 `baseline`으로 남긴다.
- **저장물**: `adapter.pt`(어댑터와 주입 설정만), `config.json`, `log.jsonl`. 평가할 때마다 어댑터를 덮어쓴다.

## 계획서 대비 변경

| 항목 | 계획 | 구현 | 이유 |
|------|------|------|------|
| 캐시 `--batch-moves` 기본값 | 1024 | 256 | 아래 발견 사항 1 |
| 평가 정밀도 | 언급 없음 (AMP 전제) | float32 기본, `--eval-amp`로 변경 가능 | 아래 발견 사항 2 |
| 평가 묶음 크기 | 언급 없음 | `--eval-max-moves` 기본 256 추가 | 발견 사항 1과 같은 이유 |
| 어댑터 저장 | `adapter.pt` | 주입 설정(rank, alpha, dropout, targets)을 함께 저장하고 `load_adapter`가 그 설정대로 주입 | 어댑터만 보고 올바르게 복원할 수 있게 함 |
| 그 밖의 옵션 | — | `--max-steps`, `--eval-positions`, `--warmup-steps`, `--grad-clip`, `--weight-decay`, `--log-every`, `--num-workers`, `--data-dir` | 짧은 확인 실행과 테스트에 필요 |

혼합 정밀도는 bfloat16이라 GradScaler를 쓰지 않는다. 캐시 파일명은 `--base` 파일명을 따른다 (`270M.pt` → `base_q_270M.npz`).

## 발견 사항

1. **한 번에 넣는 양을 키워도 빨라지지 않고, GPU 메모리를 넘기면 수십 배 느려진다.** float32 추론 처리량은 합법수 128개 이상에서 일정했다 (136M 약 890 수/초, 270M 약 450 수/초). 1,024개에서는 PyTorch가 잡아 둔 메모리가 12GB를 넘어 136M 64 수/초, 270M 29 수/초로 떨어졌다 (WSL이 시스템 메모리를 빌려 쓰는 상태). 그래서 캐시와 평가의 기본값을 256으로 잡았다.
2. **bfloat16은 q를 눈에 띄게 바꾼다.** float32 대비 q 차이가 평균 약 5e-4, 최대 약 1e-2~2e-2였다. T=0.02, τ=0.02에 비해 작지 않다. 학습 전 어댑터(베이스와 같은 모델)를 bfloat16으로 평가하면 베이스 기준선과 어긋났고(모방 손실 1.3561 → 1.3588, top-1 0.656 → 0.650), float32로는 정확히 일치했다. 그래서 캐시와 평가는 float32를 기본으로 했다. 학습의 순전파는 계획대로 bfloat16이다. 학습도 float32로 하려면 `--no-amp`를 쓰면 되지만 속도 영향은 재지 않았다.
3. **q 캐시 생성이 오래 걸린다.** 세 기사 합계 합법수가 약 900만 개라, 로컬 GPU 기준 float32로 136M 약 2.8시간, 270M 약 5.6시간으로 추정된다 (실측 처리량에서 계산한 값이며 전체를 돌려 보지는 않았다). `--amp`를 주면 약 2.5배 빠르지만 발견 사항 2의 오차가 캐시에 들어간다.
4. **학습 속도**: 136M, 국면 32개 배치, 한도 128에서 갱신당 약 1.3초(국면 약 25개/초), 최대 GPU 메모리 4.6 GiB였다. 이 속도면 로컬 GPU에서 탈 1 epoch(79,493국면)이 약 53분, 세 기사 3 epoch이 약 9시간이다 (추정).
5. **기본 학습률에서는 변화가 느리다.** 60스텝으로는 val 지표가 사실상 그대로였다. 아래 315스텝 확인 학습에서도 모방 손실은 내려갔지만 top-1 일치율은 움직이지 않았다. 학습량이 본 학습의 약 4%에 불과한 실행이라 하이퍼파라미터가 부적절하다는 근거로 보기는 어렵다. 본 학습 첫 결과를 보고 판단할 사항이다.
6. **기력 항은 여전히 작다.** 학습 중 기력 항은 0.005 안팎으로 모방 항(1.3~1.8)의 0.3% 수준이다. 확인 학습에서 regret이 늘지 않았으므로 지금 설정에서 문제를 일으키지는 않았지만, λ=1.0에서 기력 항이 실제 제약으로 작동하는지는 이 실행으로 알 수 없다.

## 검증

- `pytest`: 101 passed, 0 failed (환경 6 + 전처리 38 + 모델 23 + LoRA 7 + 손실 11 + 학습 16)
  - 캐시의 수 순서가 `policy.py`의 순서와 일치하고, q가 모델 출력과 일치하며, 한 번에 넣는 양과 무관
  - collate: 가변 합법수 묶기, 목표 수 위치, 캐시 q 정렬
  - 캐시 없음·국면 수 불일치·수 순서 불일치는 오류
  - 묶음 분할 (한도 1, 30, 64, 128, 10,000): 합법수 합계가 한도 이하, 국면이 쪼개지지 않음, 순서·총 개수 보존, 한도보다 큰 국면은 단독 묶음
  - **기울기 누적**: 한 번에 역전파한 기울기와 묶음으로 누적한 기울기가 일치 (한도 1, 64, 128, γ=0과 1), 한도가 달라도 한 스텝 뒤 어댑터 가중치가 일치
  - 평가 지표가 손계산 값과 일치, 학습 전 어댑터의 지표가 베이스 기준선과 일치
  - 학습률 스케줄 (워밍업, 코사인)
  - 스모크: 소형 모델로 캐시 → 학습 6스텝 → 어댑터 저장 → 새 베이스에 재로드, 재로드한 지표가 학습 직후와 일치
- **CPU 전체 파이프라인** (계획서의 로컬 스모크 테스트): 탈 PGN 전처리(6초, 기존 결과와 바이트 단위로 동일) → 앞 300/100국면 → 소형 무작위 모델로 캐시 → 학습 3스텝 → 어댑터 재로드. 오류 없이 완주했고 재로드 평가가 마지막 평가와 일치했다 (모방 손실 3.821163).
- **로컬 GPU 136M 확인 학습**: 탈 train 앞 2,000국면 / val 앞 500국면, 기본 설정(rank 16, lr 1e-4, 국면 32개, 한도 128, T 0.02, τ 0.02, λ 1.0), 5 epoch = 315스텝, 477초.

  | 시점 | 모방 손실 | top-1 | top-3 | regret | 밴드 이탈률 |
  |------|-----------|-------|-------|--------|-------------|
  | 베이스 기준선 | 1.3561 | 0.656 | 0.896 | 0.0116 | 0.2269 |
  | 63스텝 (1 epoch) | 1.3513 | 0.658 | 0.894 | 0.0115 | 0.2264 |
  | 126스텝 | 1.3348 | 0.658 | 0.896 | 0.0114 | 0.2248 |
  | 189스텝 | 1.3160 | 0.658 | 0.894 | 0.0113 | 0.2230 |
  | 252스텝 | 1.3093 | 0.656 | 0.896 | 0.0113 | 0.2224 |
  | 315스텝 (5 epoch) | 1.3082 | 0.656 | 0.896 | 0.0113 | 0.2223 |

  val 모방 손실이 1.3561 → 1.3082로 내려갔고(−3.5%) regret과 밴드 이탈률은 늘지 않았다. top-1/top-3 일치율은 변하지 않았다. 손실은 유한했고 최대 GPU 메모리는 4.61 GiB였다.
- 세 기사에 대해 `--player`만 바꿔 같은 명령으로 실행되는 구조다. 기사별 차이는 `src/players.py`와 데이터 폴더뿐이다.

### 검증의 한계

- 확인 학습은 탈 한 명, train 2,000국면(전체의 2.5%), val 500국면이다. val 500국면에서 top-1의 0.2%p는 국면 1개 차이라 일치율 변화를 판단할 수 없다.
- 카르포프·스미슬로프와 270M으로는 학습을 돌리지 않았다. 270M은 3단계에서 메모리(한도 128에서 9.2 GiB)만 확인했다.
- 전체 데이터에 대한 q 캐시 생성과 본 학습은 하지 않았다. 소요 시간은 처리량에서 계산한 추정치다.
- 학습 재개(resume) 기능은 없다. 중단되면 처음부터 다시 돌려야 한다 (마지막 평가 시점의 `adapter.pt`는 남는다).
- GPU 서버에서는 실행하지 않았다. 계획서대로 본 학습은 작업지시자가 실행한다.
