# Task #5 1단계 완료 보고서: 기록 대조와 영향 추정

## 요약

- 세 기사 학습의 중단·재개 사실을 로그에서 다시 뽑았다. 기존 기록과 다른 곳은 **탈의 중단 지점**과 **스미슬로프의 중단 지점·잃은 갱신 수**다.
- 수정 전 코드가 실제로 쓴 데이터 순서를 실제 `DataLoader`와 `ResumableBatchSampler`로 다시 만들었다. 재개한 epoch에서 두 번 학습되고 대신 한 번도 학습되지 않은 국면이 탈 6.35%, 카르포프 0.83%(epoch 1)와 5.48%(epoch 2), 스미슬로프 12.45%였다.
- 소스는 수정하지 않았다. 트러블슈팅 문서 초안을 썼다 (`mydocs/troubleshootings/resume_data_order.md`).

### 기존 기록과의 차이

| 기사 | 기존 기록 | 로그 |
|------|------|------|
| 탈 | step 4800~4820 사이에서 중단 | step **5000~5020** 사이에서 중단, 잃은 갱신 200~219 |
| 스미슬로프 | step 5,400~5,420 사이에서 중단, 잃은 갱신 20개 이내 | step **5580~5600** 사이에서 중단, 잃은 갱신 **180~199** |
| 카르포프 | 체크포인트 저장 직후 종료, 잃은 갱신 몇 개 이내 | 맞음 |

- 잃은 시간: 스미슬로프는 체크포인트 5400 뒤 기록된 구간이 225초다. 기록되지 않은 최대 19 갱신(약 25초)과 재시작 22초를 더하면 약 4~4.5분이다. 기존 "약 4분"은 크게 틀리지 않았다. 탈은 260초 + 최대 약 25초 + 22초로 약 5분이다.
- 기존 기록이 틀린 이유는 재개한 시도의 `{"type": "resume"}` 줄과 그 뒤의 train 줄만 보고, 실패한 시도의 마지막 train 줄을 확인하지 않았기 때문으로 보인다. `log.jsonl`은 재개할 때 체크포인트 뒤의 줄을 잘라 내므로 실행 로그로만 확인할 수 있다.

## 2. 수정 전 순서 시뮬레이션

### 방법

- 수정 전 코드(`local/task5` HEAD)의 `ResumableBatchSampler`와 실제 `DataLoader(num_workers=2, persistent_workers=True, generator=generator)`를 쓴다. 데이터셋 대신 `range(국면 수)`를 넣는다.
- 학습 루프의 순서 관련 부분(`train.py`의 생성기·샘플러·로더 생성, epoch 시작 때 상태 저장, 재개 때 상태 복원과 건너뛰기)을 그대로 옮긴다. 모델 대신 배치 인덱스를 모은다.
- 시도마다 새 프로세스처럼 생성기·샘플러·로더를 새로 만들고, 앞 시도의 마지막 체크포인트 위치(epoch, 끝낸 배치 수, epoch 시작 때 생성기 상태)에서 시작한다. 체크포인트 뒤에 버려진 갱신은 세지 않는다.
- 실제 `DataLoader`를 쓰므로 계획서의 "흉내와 실제 `DataLoader` 대조"는 따로 할 필요가 없다. 대신 루프를 옮긴 부분이 맞는지 아래 점검으로 확인했다.

### 루프 점검 (데이터 4,000개, epoch당 125 배치, 3 epoch)

| 경우 | 끊기지 않은 학습과 다른 배치 수 (epoch 0 / 1 / 2) |
|------|------|
| `num_workers=0`, step 200·260에서 재개 | 0 / 0 / 0 |
| `num_workers=2`, step 200·260에서 재개 | 0 / 50 / 125 |
| `num_workers=2`, step 200에서 한 번 재개 | 0 / 50 / 125 |

- `num_workers=0`에서 같다는 것은 기존 재개 테스트 결과와 맞는다. 옮긴 루프가 재개 로직을 제대로 따른다는 뜻이다.
- `num_workers=2`에서는 재개한 epoch의 나머지와 그 뒤 epoch 전체의 순서가 다르다.

### 세 어댑터의 집계 (실제 국면 수, 시도 기록)

| 기사 | epoch 0 | epoch 1 (2회 / 0회) | epoch 2 (2회 / 0회) | 3 epoch 합계 횟수 분포 |
|------|------|------|------|------|
| 탈 | 모두 1회 | 5,045 / 5,045 (6.35%) | 모두 1회 (순서는 다름) | 2회 5,045 · 3회 69,403 · 4회 5,045 |
| 카르포프 | 모두 1회 | 801 / 801 (0.83%) | 5,279 / 5,279 (5.48%) | 1회 52 · 2회 5,895 · 3회 84,487 · 4회 5,919 · 5회 40 |
| 스미슬로프 | 모두 1회 | 11,597 / 11,597 (12.45%) | 모두 1회 (순서는 다름) | 2회 11,597 · 3회 69,984 · 4회 11,597 |

- 끊기지 않은 학습으로 같은 시뮬레이션을 돌리면 세 기사 모두 국면마다 epoch당 1회였다 (스크립트의 assert로 확인).
- 갱신 수와 학습한 국면의 총량은 계획과 같다. 달라진 것은 국면별 학습 횟수와 배치 순서다.
- 시뮬레이션 실행 시간은 세 기사를 합쳐 29초(CPU)였다.

## 3. 한계

- 실제 학습의 배치 내용은 로그에 없어 직접 대조하지 못했다. 겹치는 step의 loss가 첫 기록부터 다르다는 점만 시뮬레이션과 맞는다.
- 성능 영향은 실측하지 않았다 (작업지시자 결정).

## 사용한 스크립트 (스크래치패드, 저장소 밖)

- `attempts.py`: 실행 로그의 `=== {player} 시도 N 시작/실패/완료` 줄과 train 줄로 시도별 표, 겹치는 step 비교표를 만든다.
- `simulate.py`: 위 방법대로 시도별로 순서를 다시 만들고, `np.zeros((3, 국면 수))`에 epoch별 학습 횟수를 더한다. 끊기지 않은 학습은 모두 1회인지 assert로 확인한다.
- `check_sim.py`: 작은 데이터로 `num_workers` 0과 2에서 끊기지 않은 학습과 재개한 학습의 배치를 하나씩 대조한다.
