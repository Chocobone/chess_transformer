구현 계획서의 대상 표에 더해 아래 패턴으로 `mydocs/` 전체를 훑었다. 이번 타스크 자신의 문서(계획서, Task #5 보고서, 트러블슈팅, 오늘할일 20261015)는 제외했다.

```

| num-workers.{0,40}바꿔도 | 잃은 갱신 | 잃은 시간 | 약 4분 | 1,840 | 4,000 갱신 | 4800 | 5400 | 5420
```

계획서 표에 없던 대상으로 아래를 찾았다.

- Task #2 보고서·2단계 보고서의 "서로 다른 지점(1,840 / 4,000 / 4,800 갱신 부근)"
- Task #2 테스트 결과의 "재개 기능 확인 (136M, GPU)" 절 (epoch 0 안에서만 끊은 확인)

정정하지 않은 것과 그 이유:

| 기술 | 이유 |
|------|------|
| 탈 1차 "1,840 갱신 직후", 2차 "step 4000 평가 직후" | 실패한 실행의 마지막 train 줄과 맞다 (1840, 4000). 재개가 없던 실행이라 순서 문제도 없다 |

- 표 셀과 한 줄짜리 항목에는 원문 뒤에 `[정정 (2026-10-15, Task #5): …]`를 붙였다.

## 4. 트러블슈팅 문서

`mydocs/troubleshootings/resume_data_order.md`에 "기존 기록 정정"과 "재발 방지" 절을 더해 완성했다.

- 기존 기록이 틀린 이유: `log.jsonl`은 재개할 때 체크포인트 뒤의 줄을 잘라 낸다. 그래서 실패한 시도의 진행은 실행 로그에만 남는다. 앞으로 중단 지점은 실행 로그에서 실패한 시도의 마지막 train 줄로 적는다.
- 재발 방지: `num_workers` > 0과 epoch 경계를 넘기는 재개 테스트를 넣었다. GPU로 재개를 확인할 때는 epoch 경계를 넘기는 길이로 확인한다.
